# nadav-design · mode `redesign`

## Mode `redesign` (the whole app: the direction as a standalone demo, one review round, a tag, a build plan; no app code)

Part of the nadav-design skill. Before this file read the Hard rules of `SKILL.md`, then `shared/rules.md`
and `shared/platform.md`. Every path here is relative to the skill folder, one level above this file.


Read `redesign/README.md` (in the skill folder) before step 0 and follow it step by step: it holds the procedure, the tools (`redesign/tools/`), the templates and the workflow scripts. Generalized from the SporChat v4 redesign (22.9–11.10.2026). This mode never writes into the app repo (not even `.omc/`): the demo, the decisions, the debts, the run log and the build plan live in an output repo of its own, and the build session that START-BUILD opens after Nadav approved the plan takes every screen through `screen`'s gates.

For an app this mode's page carries the direction, not every screen: the design language, the inventory, the main journey as one playable flow, the shared components and design values, and the decisions. It gets one review round with Nadav, is tagged and frozen when he approves the direction, and the tag leads to the build plan. Only after he approves that plan does the build session start; its first unit is the app's own preview on invented data, isolated from everything real, where it designs every other screen and state under `screen`'s gates and shows each one to him playing once the preview's check script passes (nobody plays it before). Approving the direction never starts work in the app repo (`shared/built-once.md`, «An app is built once»: the why, the preview's isolation, MediZen and SHIFTS, and what it does not cover).

0. **Preconditions and scale.** Declare the tempo and the track. Read the app (routes, components, states, DESIGN.md/PRODUCT.md when present, users), count screens, size the run (README «Scale»). Pin the app's commit. Output folder outside the repo and outside `/tmp` (`~/design-redesign/<app>/`), its own git repo, set up as README step 0 lists. Evidence: the app's commit, the counts, the sizing, `git log -1`.
1. **Design language.** BRIEF.md from the app's own character, on DESIGN.md/PRODUCT.md when they exist; never another app's look or the generic Impeccable look, never `craft`/`bolder`/`overdrive`. Nadav approves (AskUserQuestion, recommendation first). Evidence: the approved BRIEF.md and two or three phones in it.
2. **Inventory.** INVENTORY.md (every screen, state and control today), STORY.md (the main journey), today's look from the sources README step 2 lists in order (a screen none can capture is drawn as «היום · לא צולם»). Evidence: the files and `ls today/`.
2b. **Baseline: today's numbers for the main tasks** (Nadav asked for this step on 13.11.2026). For each main task STORY.md names, as the app is today: how many complete it out of how many start, the median time from start to finish, and the errors per attempt (a step back, a rejected field, a tap that did nothing). Source, in this order: PostHog, read-only, the last 28 days of the task's start and finish events (a funnel), with the privacy defaults of the global rules (nothing that names a person in what is copied out); or, where the app has no such events, the session with people of `ship` step 6b, run on today's app, each task timed and its errors counted by the one who watches. Write dated `baseline` rows into `MEASURES.md` of the output repo (template `redesign/templates/MEASURES.md`: one file per project, rows added, never rewritten); unit 1 of the build plan moves them into the app's `docs/ui-audit/MEASURES.md`. A task that cannot be measured gets a row `not taken` with the reason, and the redesign goes on. Evidence: the rows and where each number came from.
2c. **The menu with people** (an owner step: only people can do it, so an agent prepares and records but never answers; only for a large app: more than 20 screens reachable from the menu, or more than 7 items at its first level, bar and «עוד» together, a threshold this skill chose). `plan` step 3b says what is run, with whom, what is recorded and what changes the menu; here it runs on today's menu tree and its tasks come from STORY.md, before step 3 draws the new navigation, and it writes `NAV-TEST-<date>.md` into the output repo. Skipped with "small app" or "no people yet", said in the RUN-LOG. Evidence: the file, or the skip line.
3. **Direction demo.** Shared components from BRIEF.md first, then the main journey of STORY.md as one playable flow (`proto/index.html`), with a section per screen the journey passes through: «היום», «אחרי», and a «מצב» phone for every state INVENTORY.md lists for that screen (README step 3; `workflows/demo-round.js` holds its builders and words verifier to it); dark, light and 320; RTL-first, real copy, 44px, 4.5:1, local files only. Screens off the journey are not drawn here; they are designed in the app's preview after the plan is approved. `tools/build.py`, `tools/shoot.mjs`. Evidence: the prototype link, the build line and clean reports.
4. **Questions.** DECISIONS-OPEN.md, asked in AskUserQuestion batches of up to 4, recommendation first; answers numbered in DECISIONS-ANSWERED.md, never re-decided.
5. **New features.** On the journey, «חדש · מאושר» or «מוצע · <date> · אחרי הליבה · <title>» phones with the note under the phone; off the journey, a FEATURES-PROPOSED.md row only, designed later in the app's preview. Every row is carried into the plan.
6. **One review round, then the tag.** Fix lanes by screen group with cross-lane requests, rebuild, fresh Opus verify by lenses (craft, words and sources, the STORY), ONE full sweep then targeted confirms that account for every finding id (≤3). Green only when all of it holds (README «Green means all of it»). The page shown to him is also checked at the width he sees it at (`rules/working-style.md`, Verification). Then Nadav answers keep/change/revert on CHANGES-<date>.md; his change and revert answers are applied by a fix run of the same round, and he approves the direction (AskUserQuestion). The approved commit is tagged and the page is read-only from then on: a later design change goes to the plan and is made in the app's preview, never in another round here. If he does not approve the direction, ask him how to go on; a second round is never started on its own, and no answer of his starts work in the app repo before a build plan he approved. `redesign/workflows/demo-round.js` only when Nadav opted into multi-agent orchestration; otherwise subagents one by one, with the model `rules/model-routing.md` names for the role. Evidence: the round's `gates`, his answers, the tag.
7. **History.** `pre/` before every edit, `after/` shots, a dated changelog line per change, CHANGES-<date>.md in plain Hebrew per round.
8. **Build plan.** Read `shared/built-once.md` in full before this step. It names the approved tag. Unit 1 is the app's preview on invented data, isolated and checked as `shared/built-once.md`, «An app is built once», point 5, says; nobody plays the preview, on any machine, before its check script passes there. Unit 1 also moves the rows of the output repo's `MEASURES.md` into the app's `docs/ui-audit/MEASURES.md`, as they are (step 2b). Then tokens and shared components, then the screens: one the tagged demo drew cites its column labels and is held to its phones at the tag (`screen` step 8b); one it did not draw cites its INVENTORY.md row, is designed in the preview, and keeps every control and state of that row unless a numbered answer removes it. Units land as point 2 of that section says. For a standalone demo that predates that section (MediZen's), what moves to the app, what runs before the tag and what after it: `shared/standalone-demo-to-app.md`. Where Nadav asked for a from-zero run and the project has no build plan he already approved (SHIFTS, whose plan he approved, adopts the gate only when he approves a round of that plan: `shared/from-zero-runs.md`, «SHIFTS»), the plan names the look route per kind of part, starts with the instrument unit (a later run reuses its latest approved commit), puts MediZen's three measured component units first after the preview and the token unit, and keeps the two records: `shared/from-zero-runs.md`. Units cite column labels, `tools/check-anchors.py` 0 missing and 0 wrong; fresh Opus review to APPROVE, then a diff-only confirm, then the second model (`rules/working-style.md`, "Second model"; in the order `redesign/workflows/plan-review.js` names); every later edit diff-confirmed (a full review under `args.sensitive`); START-BUILD prompt and checklist (`redesign/workflows/plan-review.js`; the caller passes `sensitive: true` when the plan's units touch money, messages to people, data or official filings, `rules/working-style.md`, "Second model"). Then Nadav approves the finished plan (AskUserQuestion); reviewers approving is not him approving. Evidence: the verdicts, which second model ran, his numbered answer.
9. **Partners** (only when Nadav asks): a partner page and guide; README points to the SporChat example.
10. **Ship.** Commit the output repo, publish the demo (claude.ai artifact or Nadav's own domain, never `*.vercel.app`), report with links, and end like every mode (checklist in the output repo's `RUN-LOG.md`, gap scan, `הבא:`).

README «Operating lessons» gives each rule its why: `model: 'opus'` on every `agent()`; big data in files, never in workflow args; one browser at a time after `uptime`; a checkpoint commit per phase; restart at `spec` from the extracted state (`tools/journal-state.py`) instead of resuming past a failed agent; a reviewer is never the author; gates read structured fields, never prose.
