# nadav-design · mode `screen`

## Mode `screen <name>` (one screen, new or redesign)

Part of the nadav-design skill. Before this file read the Hard rules of `SKILL.md`, then `shared/rules.md`
and `shared/platform.md`. Every path here is relative to the skill folder, one level above this file.


1. **Brief.** Declare the tempo and the track; in a Capacitor or Expo app, `shared/platform.md` adds to or replaces steps 6-8. Write a 10-line brief for the screen: purpose, user, data source, and every state (loading, empty, error, success), acceptance: RTL, 375 and 1440, dark mode, keyboard, touch targets >= 44px, reduced-motion, real Hebrew copy, tokens only. If the screen renders content a user typed or uploaded, the brief also lists its hostile cases (mixed Hebrew and Latin on one line, a 300-character word, a pasted URL, an emoji-only entry, a failed upload, a reported item) and the `.claude/rules/ui.md` user-content rules apply. In a redesign build, a screen the approved demo did not draw also lists its INVENTORY.md row (every control, state and role variant) as acceptance: each one is in the preview, or a numbered answer in DECISIONS-ANSWERED.md removes it; a control missing without one stops the screen and goes to Nadav (standard S-04). A reviewer checks this against the row, because the capability diff tool that would check it by machine is not in this skill on main yet. Show it; wait for OK.
2. **Build or redesign** with shadcn components only (add via `PM dlx shadcn@latest add <name>`), tokens from globals.css, logical properties. For a redesign: keep behavior, strings, routes and data code unchanged. When the app has a preview on invented data, the screen is built and shown in it, and in a redesign build a screen the approved demo did not draw is designed here, from BRIEF.md and the shared components; the demo at its tag is reference and is never edited (`shared/rules.md`, «An app is built once»).
3. `/impeccable critique` on the screen (the skill names it, per the carve-out in guides/ui-routing.md).
4. Fix what it named with Impeccable's own fixers, inside the existing design language: `/impeccable polish` for the P0/P1 findings, then `/impeccable harden` (edge cases, long text, RTL, states). Nadav types both; you apply nothing by hand that these two cover.
5. If the screen has motion: ask Nadav to type `/nadavai:review-animations` (user-invoked by design); apply the Block items.
5b. **Second opinion, only when the screen is critical** (auth, signup, onboarding, checkout, payment, account deletion) or introduces a new complex component: `/interfaces:interface-review` on the working tree; apply HIGH findings. For a new complex component also `/interfaces:break` and fix what breaks. For auth, payment, account deletion or anything touching data or money also the second model on the diff (`rules/working-style.md`, "Second model"); report its findings and what was done with them. Otherwise skip this step and say "skipped: not critical".
6. On the screen's files only (`FILES=$( { git diff --name-only HEAD -- UI_DIRS; git ls-files --others --exclude-standard UI_DIRS; } | grep -E '\.(tsx?|jsx?)$' )`; if it is empty, skip this step and say so, never run the tools without arguments): `PM exec impeccable detect $FILES` clean and `npx eslint --fix --max-warnings=0 $FILES` clean (never the whole repo inside a one-screen task; the pre-commit hook and CI run the full pass); then the Vercel web-design-guidelines skill as a static lint on the changed files (a11y, forms, focus, animation, Intl), and `vercel-react-best-practices` + `vercel-composition-patterns` on the same files (waterfalls, bundle, memo, composition); fix the findings or explain each one left.
7. **Blast radius first.** If the diff touched anything shared (a file under `components/`, a layout, `TOKENS` or `base.css`), list every route that imports it (`grep -rl "<ComponentName>" UI_DIRS`) and run the DoD on all of them, not only this screen; when it is a token or a layout, run every route (through `heavy-slot --`). Say the number of routes the change affects before running. Only when the diff is confined to this screen's own files: `PM dod -- --grep "<slug>__"` for this route only (run `node e2e/dod/routes.mjs` first so the route and its state variants are in `routes.json`; the all-routes run belongs to audit and ship); read that route's score in `reports/dod/dod.json`. Score must be 100 (no landing runs the DoD yet: see the quality bar). A deduction that cannot be fixed stops the step (Hard rules): report it with the cause, do not commit the screen.
8. Open the four screenshots the DoD run just wrote (`reports/dod/screens/<slug>__{375,1440}__{light,dark}.png`); do not take them again. Show them to Nadav next to the before shots (in a redesign build, for a screen the tagged demo drew, also next to its phones at the tag), with a link to the screen playing in the app's preview when the app has one and its check script, apart from the no-demo check, passes on this tree, and apply the **visual change gate**: he says keep, change or revert, for each thing he names. Fix what he names and re-run step 7. Nothing is committed on my own judgement of how it looks.
8b. **Approval in a separate lane (never self-approve).** Spawn the `oh-my-claudecode:verifier` agent with `model: opus`, the diff, the DoD score and the four screenshots; it checks the brief's acceptance list from step 1, and in a redesign build the screen's INVENTORY.md row item by item against the preview (each present, or the numbered answer that removes it). In a redesign build, for a screen the tagged demo drew, the verifier is also given that screen's phones at the tag (`tools/shoot.mjs` on a checkout of the tag `demo-approved-<date>`, its `labels.json` naming each phone) and checks them control by control, state by state, against the preview shots; a control or state on those phones that is missing in the preview with no numbered answer in DECISIONS-ANSWERED.md removing it stops the screen and goes to Nadav. This is the weaker check: the scripted parity tool that would compare them by machine is not in this skill on main. Commit only on its approval (under `flow`, local until his answer); on rejection go back to the step it names.
9. Commit with Conventional Commits; tick the screen's checkbox in `docs/specs/*.md` and its items in `docs/ui-audit/PLAN.md` where they exist. Report: score, screenshot paths, what changed, and what was left out with its decided home (PLAN item or DESIGN.md exception; never an open sentence). Ask before starting another screen (tempo: `shared/rules.md`).

Optional after a critical screen, only if Nadav asks: `/interfaces:interface-review`, `/interfaces:break`.
