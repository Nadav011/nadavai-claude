# nadav-design · mode `screen`

## Mode `screen <name>` (one screen, new or redesign)

Part of the nadav-design skill. Before this file read the Hard rules of `SKILL.md`, then `shared/rules.md`
and `shared/platform.md`. Every path here is relative to the skill folder, one level above this file.


1. **Brief.** In an app that has a preview on invented data, read `shared/built-once.md` in full first. Declare the tempo and the track; in a Capacitor or Expo app, `shared/platform.md` adds to or replaces steps 6-8. Write a 10-line brief for the screen: purpose, user, data source, and every state (loading, empty, error, success), acceptance: RTL, 375 and 1440, dark mode, keyboard, touch targets >= 44px, reduced-motion, real Hebrew copy, tokens only; the rules of group 9 of `standard/experience.md` (A-01 to A-03), and of group 8 (H-01 to H-07) when the screen asks for a consent, money or a commitment or is a way out of one, as items step 8b's verifier reads, with the route's `reports/dod/results/extended/<slug>.json` from step 7's run where it exists (those checks never move the score). If the screen renders content a user typed or uploaded, the brief also lists its hostile cases (mixed Hebrew and Latin on one line, a 300-character word, a pasted URL, an emoji-only entry, a failed upload, a reported item) and the `.claude/rules/ui.md` user-content rules apply. In a redesign build, a screen the approved demo did not draw also lists its INVENTORY.md row (every control, state and role variant) as acceptance: each one is in the preview, or a numbered answer in DECISIONS-ANSWERED.md removes it; what happens to an item (a control, a state or a role variant) that is missing without one is said once, in step 8b («A missing item»), and holds here. A reviewer checks this against the row, because the capability diff tool that would check it by machine is not in this skill on main yet. Show it; wait for OK.
2. **Build or redesign** with shadcn components only (add via `PM dlx shadcn@latest add <name>`), tokens from globals.css, logical properties. For a redesign: keep behavior, strings, routes and data code unchanged. When the app has a preview on invented data, the screen is built and shown in it, and in a redesign build a screen the approved demo did not draw is designed here, from BRIEF.md and the shared components; the demo at its tag is reference and is never edited (`shared/rules.md`, «An app is built once»). When a screen's look is not already decided (no tagged demo or approved direction decides it; a screen they decide is case 1 of the visual change gate and outside this sentence), what Nadav sees first is a rough prototype made in minutes in the app's approved look (`standard/experience.md`, B-03), shown to him at once in AskUserQuestion (a link he can open, or two or three options), before any polish or review round, and that screen is not polished, reviewed or built on until he answers; work that does not depend on his answer carries on, under `flow` and `close-first` alike (`rules/working-style.md`, Requests: Nadav, 2026-11-14, «דברים שאני יכול למנוע סבבים שלהם אתה עוצר במקום ומראה ולא מתקדם»; which pieces count is the agent's reading there). Every gate before a commit (the DoD, step 8b, the visual change gate) is unchanged. The prototype is built where this step builds, on invented data, in the app's preview where one exists and as `shared/built-once.md` allows (points 5 and 6), shown at his width; never on real data, never as a separate page, and never committed as the screen. Why: on the SHIFTS sign-in, 14.11.2026, round 0, he rejected on sight a plain form in the repo's default grey tokens («ממש מכוער», `standard/rejected.md`), and the rough rounds drawn in minutes after it were accepted as a direction; that it failed because nine review reads came before he saw it is the session's reading [I].
3. `/impeccable critique` on the screen (the skill names it, per the carve-out in guides/ui-routing.md).
4. Fix what it named with Impeccable's own fixers, inside the existing design language: `/impeccable polish` for the P0/P1 findings, then `/impeccable harden` (edge cases, long text, RTL, states). The agent runs both: they are agent-invocable, and `rules/working-style.md` ("UI and product work") names them for an existing app; apply nothing by hand that these two cover.
5. If the screen has motion: ask Nadav to type `/nadavai:review-animations` (user-invoked by design); apply the Block items.
5b. **Second opinion, only when the screen is critical** (auth, signup, onboarding, checkout, payment, account deletion) or introduces a new complex component: `/interfaces:better-interface` on the changed screens; apply HIGH findings. `/interfaces:interface-review` on the working tree can be started only by Nadav (it is user-only), so it runs when he types it, and without him this step runs `/interfaces:better-interface` (`rules/working-style.md`, "UI and product work"). For a new complex component also stress it and fix what breaks: `/interfaces:break` is user-only too and the rule names no fallback, so the agent's path [I] is `/impeccable harden` on that component (long, short and empty text, emoji and mixed-direction text, many items and none, error and loading states) and `/intent:fortify` on its states; `/interfaces:break` runs when Nadav types it. For auth, payment, account deletion or anything touching data or money also the second model on the diff (`rules/working-style.md`, "Second model"); report its findings and what was done with them. Otherwise skip this step and say "skipped: not critical".
6. On the screen's files only (`FILES=$( { git diff --name-only HEAD -- UI_DIRS; git ls-files --others --exclude-standard UI_DIRS; } | grep -E '\.(tsx?|jsx?)$' )`; if it is empty, skip this step and say so, never run the tools without arguments): `PM exec impeccable detect $FILES` clean and `npx eslint --fix --max-warnings=0 $FILES` clean (never the whole repo inside a one-screen task; the pre-commit hook and CI run the full pass); then the Vercel web-design-guidelines skill as a static lint on the changed files (a11y, forms, focus, animation, Intl), and `vercel-react-best-practices` + `vercel-composition-patterns` on the same files (waterfalls, bundle, memo, composition); fix the findings or explain each one left.
7. **Blast radius first.** If the diff touched anything shared (a file under `components/`, a layout, `TOKENS` or `base.css`), list every route that imports it (`grep -rl "<ComponentName>" UI_DIRS`) and run the DoD on all of them, not only this screen; when it is a token or a layout, run every route (through `heavy-slot --`). Say the number of routes the change affects before running. Only when the diff is confined to this screen's own files: `PM dod -- --grep "<slug>__"` for this route only (run `node e2e/dod/routes.mjs` first so the route and its state variants are in `routes.json`; the all-routes run belongs to audit and ship); read that route's score in `reports/dod/dod.json`. Score must be 100 (no landing runs the DoD yet: see the quality bar). A deduction that cannot be fixed stops the step (Hard rules): report it with the cause, do not commit the screen.
8. Open the four screenshots the DoD run just wrote (`reports/dod/screens/<slug>__{375,1440}__{light,dark}.png`); do not take them again. Show them to Nadav next to the before shots (in a redesign build, for a screen the tagged demo drew, also next to its phones at the tag), with a link to the screen playing in the app's preview when the app has one and its check script, apart from the no-demo check, passes on this tree; a screen shown to him is also checked at the width he sees it at (`rules/working-style.md`, Verification). Apply the **visual change gate** (SKILL.md): every visible change is sorted into its case, a change that is his goes to him with AskUserQuestion while what does not depend on it goes on, and what he names is fixed and step 7 re-run. Nothing is committed without step 8b's approval.
8b. **Approval in a separate lane (never self-approve).** Spawn the `nadavai:reviewer` agent with `model: opus`, the diff, the DoD score, the four screenshots and, when the app has a preview whose check script passes on this tree (step 8), the link to the screen in it: the reviewer opens the preview itself for what the four screenshots do not show (the other states, the keyboard, reduced motion) and checks states there; it checks the brief's acceptance list from step 1, and in a redesign build the screen's INVENTORY.md row item by item against the preview (each present, or the numbered answer that removes it). In a redesign build, for a screen the tagged demo drew, the reviewer is also given that screen's phones at the tag (`tools/shoot.mjs` on a checkout of the tag `demo-approved-<date>`, its `labels.json` naming each phone) and checks them control by control, state by state, against the preview (its shots for the default state, the opened preview for the others). **A missing item** (a control, a state or a role variant on those phones or in that INVENTORY.md row that is not in the preview, with no numbered answer in DECISIONS-ANSWERED.md removing it): A missing item never passes without his numbered answer: it is a must-fix that goes back to the step it belongs to and is put in. It goes to Nadav, and the screen stops, only when the brief or the diff says in a sentence that this build drops that item or changes what it does (the visual change gate, case 3; standard S-04); until he answers, the item stays. Absence, the standard and silence are not that sentence, the reviewer does not infer it, and when the builder and the reviewer disagree it goes to Nadav. This is the weaker check: the scripted parity tool that would compare them by machine is not in this skill on main. Commit only on its approval (under `flow`, local until his answer); on rejection go back to the step each must-fix item belongs to.
9. Commit with Conventional Commits; tick the screen's checkbox in `docs/specs/*.md` and its items in `docs/ui-audit/PLAN.md` where they exist; add to `docs/ui-audit/MEASURES.md` one `gate` row per finding the gates of this run found on the screen (step 7's DoD, step 8b's verifier, the reviewers), its `ref` the finding as its gate names it and `words` the file it was read from; a finding already in the table from an earlier run of this screen, under the same `ref`, gets no second row (SKILL.md, «Owner catches»). Report: score, screenshot paths, what changed, each bug fixed on the way and each standard gap closed (their own commits, the gaps with before and after screenshots), a shared component or token fix with the screens captured before and after, the whole-app additions proposed to Nadav (SKILL.md, «No open debt, ever»), and what was left out with its decided home (a PLAN item only for what cannot be closed inside this screen, or a DESIGN.md exception; never an open sentence). Ask before starting another screen (tempo: `shared/rules.md`).

Optional after a critical screen, only when Nadav types them (both are user-only): `/interfaces:interface-review`, `/interfaces:break`.
