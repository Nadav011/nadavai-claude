# nadav-design · mode `ship`

## Mode `ship` (before release and after)

Part of the nadav-design skill. Before this file read the Hard rules of `SKILL.md`, then `shared/rules.md`
and `shared/platform.md`. Every path here is relative to the skill folder, one level above this file.


0. **Pre-flight.** Declare the tempo and the track. Every **Setup artifact** (Hard rules) exists or stop with the missing list. The QA credentials resolve and the last DoD run has `unreachable = 0`. `git status` clean, the release sha has a green landing (`ci-wait <repo> <sha>`, which covers the build; run `PM build` locally only in a repo without NadavAI CI) and the last nightly `nadavai-ui` on main is green; a red nightly blocks ship (`shared/rules.md`, «Where checks run»), and if `docs/ui-audit/PLAN.md` exists every P0 in it is closed; `REFERENCE.md`, if any, has 0 open rows. Evidence: the checklist.
1. **Full audit.** Lighthouse from the nightly when it ran it on the release tree, otherwise `heavy-slot -- PM exec lhci autorun` with every route from `e2e/dod/routes.json` in `lighthouserc.json` (mobile preset), plus `chrome-devtools lighthouse_audit` (the DevTools CLI; the MCP server is off) on the three main screens for accessibility, best-practices and SEO detail (performance comes from `lhci`); the bar is the quality bar in Hard rules. Fix every failing assertion using the chrome-devtools skills (`a11y-debugging`, `debug-optimize-lcp`) and, when the app is deployed on Cloudflare, its `web-perf` skill; re-measure until `autorun` passes. Evidence: the autorun summary.
2. **Israeli accessibility and privacy.** Run the `israeli-accessibility-compliance` skill checklist; fill the accessibility statement skeleton from setup with the real facts (contact, date, known gaps); confirm the privacy page is linked and, if PostHog replay is on, that masking is in place (`maskAllInputs`, `maskTextSelector: "*"`) and routes with personal data are excluded. Evidence: both page URLs and the replay config lines.
3. **DoD.** `node e2e/dod/routes.mjs --check` passes (routes.json covers every route), the QA session logs in (`unreachable = 0`, no page skipped for permissions), then DoD = 100 on every route, styleguide included: from the nightly when it covers the release tree, otherwise `heavy-slot -- PM dod`. Evidence: `reports/dod/dod.json` and the route count.
4. **Visual regression baseline.** Argos is wired since setup: run the DoD once with `ARGOS_TOKEN` set, open the build, approve it as the baseline; from now on `argos-pr-review` reads the diffs on every PR. With no token yet, get one as setup step 13(b) says (`rules/acting-on-behalf.md`; a plan that charges is the money gate). Evidence: the build URL.
5. **Device check (by `PLATFORM`, as `shared/platform.md` lists).** Web views: the mobile-native skill checklist on a real phone or the Android emulator. Capacitor: `npx cap sync`, `npx cap doctor` clean, then the device captures and the screen-reader pass; Expo: the native form of each gate; with an iOS target also the `ios-hig-design` skill (nadavai, from wondelai) checklist. Evidence: the device captures that file lists, the checklist outputs, and each iOS item as it defines "checked on iOS".
6. **Copy pass.** `/interfaces:better-interface` on every critical screen (it dispatches to better-writing itself); check every user-facing string against the Voice section of PRODUCT.md (form of address, glossary, no slash forms, no machine-translated strings). Fix in code. Evidence: the diff of strings changed and the list left as is.
6a. **Honest choices before release** (group 8 of `standard/experience.md`, H-01 to H-07). The review of `audit` step 5b on every screen of this release that asks for a consent, money or a commitment, and on every way out of one, with the DoD's `consent-prechecked` and `consent-refuse` from step 3's run; the accessibility rows of group 9 (A-01 to A-03) read from the same run, as `audit` step 5c; where the extended results are absent, by eye as `audit` steps 5b and 5c say. Findings go to `docs/ui-audit/PLAN.md` with a priority like any other. Evidence: the list per screen, or "no such screen in this release".
6b. **Real users (the one check no tool replaces).** 3-5 people from the target audience use the preview URL on their own phone for the main job (if that URL is the app's preview on invented data, read `shared/built-once.md` in full first: who may open it and where it may be hosted), with `mom-test` questions afterwards; findings go to `docs/ui-audit/PLAN.md` as P0-P2, and each problem a person ran into on a screen is also one `user` row in `docs/ui-audit/MEASURES.md` (`before` on a preview, `after` on a released screen; `ref` the session file, the person and the problem, so it names this one problem (`SESSIONS-2026-11-20.md P2 בעיה 3`), `words` what they said; SKILL.md, «Owner catches»). Nadav invites the people; the agent sends no message in his name unless he says yes to it. Skip with "no users yet" and say so in the summary. Evidence: the findings list.
7. **SEO pass** per Nadav's rule: enable claude-seo for this project, `/seo audit` (and `/seo geo`), fix, disable. Evidence: audit summary.
8. **Metrics before launch.** `/intent:measure` to define the success metrics and the 2-3 events that mean success; confirm those events are captured in code and appear in PostHog live events from a real browser (Claude in Chrome; PostHog drops events when `navigator.webdriver` is true) (`~/nadavai/guides/posthog-init.md` step 4); then in PostHog (the four skills named here are PostHog's skill files: the plugin is off, so read each at `~/.claude/plugins/marketplaces/posthog/skills/<name>/SKILL.md`; the tool is `mcp__plugin_nadavai_posthog__exec`): `building-a-dashboard` with those metrics, one funnel for the main job, a rage-click playlist, `signals-scout-web-vitals` for field Core Web Vitals; the weekly review with Nadav runs `investigating-replay` + `assessing-heatmaps`, and `metrics-review` (nadavai) writes the summary. Evidence: the metrics list and the PostHog object URLs.
8b. **The tasks again, after the cut-over** (only when `docs/ui-audit/MEASURES.md` has `baseline` rows). Two weeks after the release that changed those tasks (this skill's choice of time; or at the first weekly review that has 14 days of data), measure the same tasks the same way as their baseline (`redesign` step 2b, each number from the same source) and add dated `after` rows. The reminder for that date is a systemd user timer on a machine that stays on, or a timer on the Oracle VM, that only notifies Nadav (`rules/working-style.md`, Sessions): its notice names the project and says "run `/ux-ship` step 8b"; the timer measures nothing itself. Worse is decided by `completed` (a lower share than the latest baseline is a finding in `docs/ui-audit/PLAN.md`); a longer median time or more errors per attempt with the same or a better share goes into the row's `note` and is shown to Nadav, not filed (this skill's choice); a number `not taken` on either side is not compared. Evidence: the rows, next to their baseline.
9. Summary with the `qa-report` skill format: check, result, evidence, what remains. Update the "UI system" line in STATUS.md to `UI system: released YYYY-MM-DD, DoD 100, Lighthouse <scores>` (the session hook reads the word "released" + date). Commit.
