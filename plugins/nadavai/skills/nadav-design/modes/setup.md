# nadav-design · mode `setup`

## Mode `setup` (one time per project)

Part of the nadav-design skill. Before this file read the Hard rules of `SKILL.md`, then `shared/rules.md`
and `shared/platform.md`. Every path here is relative to the skill folder, one level above this file.


Every setup step that changes files ends with its own commit (`chore(design): setup step N, <name>`; under `flow`, local until his answer), because each step is a checkpoint Nadav may want to revert alone; the run log `.omc/design-runs/setup-<date>.md` is appended after every step, not at the end. **A rerun verifies; it never assumes.** A file existing proves nothing about whether it is right, and an earlier run (or an older version of this skill) may have produced a half-correct one. So step 1 runs the **verification pass** below: every artifact is checked against what its step was supposed to produce, and the result is one of three, printed as a table with the evidence line for each row:

| result | meaning | what happens |
|---|---|---|
| `ok` | the check passed | the step is skipped, one line, no work |
| `repair` | the artifact exists but fails its check | its step runs again, on that gap only, with the visual change gate |
| `missing` | not there at all | its step runs in full |
| `n/a` | the check does not apply to this project | nothing runs; the row says why (never `ok`, because nothing was checked) |

**The checks (each is a command or a file read, never an impression):**
- `DESIGN.md`: `npx @google/design.md lint DESIGN.md` passes, a Foundations section exists, and its token values match `TOKENS` (spot-check the accent, the radius scale and the font).
- `PRODUCT.md`: a Voice section with form of address, tone, glossary and `he-IL` formats; the Hebrew RTL-first line present.
- `.claude/rules/ui.md`: `paths` frontmatter present, names the real token file, and the CLAUDE.md line points at it.
- `base.css`: imported by `TOKENS`, uses the Tailwind 4 namespaces (`--transition-duration-*`, `--z-index-*`) and keeps the insets in `@theme static`; compile once and confirm `duration-base` and `z-modal` produce CSS.
- Tokens: `grep -rE "#[0-9a-fA-F]{6}" UI_DIRS --include=*.tsx | wc -l` is 0, one accent, dark mode resolves, one global reduced-motion rule.
- RTL: the physical-class count is 0, `dir="rtl"` on `<html>`, the tailwind-rtl config registered and `eslint --max-warnings=0` clean.
- Fonts: `document.fonts` shows at most two families on a real page.
- Preview on invented data (step 10b, a new app only; on an existing app the row is `n/a` with "not a setup step: unit 1 of a redesign plan, or built from `plan` step 5 on his request"): its start script runs and the preview's check script exits 0 (the no-demo check on a production build, the environment check, and the planted browser and server calls blocked).
- Styleguide route: it exists, renders every token group and every installed component, and is in the DoD routes.
- DoD: `node e2e/dod/routes.mjs --check` passes, and the last `reports/dod/dod.json` has `unreachable: 0` and covers every route. **If the project built its own gate (its own routes file, its own auth setup, several verticals), that is the gate: verify it covers every route and every vertical with a QA session, and never replace it with the template.**
- Thresholds: the `minScore` and `maxNumericValue` numbers in `lighthouserc.json` equal the template's; `dod-shared.ts` matches the template by meaning, not bytes (retro step 2).
- Enforcement: `.github/workflows/ui.yml` has the DoD score gate line; `lint:ui` exists and exits 0; the global pre-commit rejects a test file containing `ml-4` (prove it, then revert).
- Release wiring: the accessibility page (and the privacy page when personal data is collected) exist with real content, not a skeleton; PostHog either reports events or CLAUDE.md says it is not used.

Print the table first, then work only the `repair` and `missing` rows, in step order, one at a time with evidence. A project where everything is `ok` ends with the table and no commit. `/ux-setup step N` runs one step regardless of its check.

   - Design docs and state: `DESIGN.md`, `design.md`, `PRODUCT.md`, `design-system.md`, `style-guide.md`, `tokens.json`, `design-plans/`, `.impeccable/`, `.superdesign/`, `superdesign/`, `.stitch/`, `.design/`, `docs/design*`, `docs/ui-audit/`, `.omc/skills/*design*`, `.omc/plans/*design*`, design entries in `.omc/notepad.md` and `.omc/project-memory.json`.
   - Rules text: sections in `CLAUDE.md` and `AGENTS.md` about design, UI, fonts, colors, motion, RTL from the old system.
   - Never touch product code (app/, components/, lib/, styles) in this step; tokens and CSS are handled in steps 2-4.
   - **Mechanical sweep, so nothing is missed.** Run `~/nadavai/plugins/nadavai/scripts/design-legacy-sweep.sh` (file names and file contents; the patterns and the allow-list of files this setup creates live in that script, nowhere else) and show its output. Add every hit to the inventory unless it is product code or a product asset.
   Show the full list with paths and one line on what each is. Ask Nadav to approve. Then: copy everything approved to `.omc/archive/design-legacy-<YYYY-MM-DD>/` (a local, untracked convenience copy; `.omc/` is git-ignored) and write the tracked `docs/archive/design-legacy-<YYYY-MM-DD>.md` manifest (paths, one line each, the commit hash that removed them); git history is the durable archive, so the removal is a normal commit, remove the old sections from CLAUDE.md/AGENTS.md/README (keep non-design rules), remove the matching hooks and settings entries, delete design entries from `.omc/notepad.md` and `.omc/project-memory.json`, and commit `chore(design): archive legacy design system before setup`.

1. **Detect.** Declare the tempo and the track. Read CLAUDE.md, package.json, the lockfile, components.json (if any), `TOKENS`, `SHELL`, `.claude/rules/*`, `.woodpecker/*`, `.github/workflows/*`, `.husky/` or `lefthook.yml`, `capacitor.config.*`, `public/manifest*`. Report: framework family (Next or Vite) + version, Tailwind version, shadcn yes/no and base, current font, `dir="rtl"` on `<html>` yes/no, count of physical direction classes: `grep -rEo "\b(-?(m|p)[lr]-|-?(left|right)-|text-(left|right)\b|rounded-[tb]?[lr]\b|rounded-[tb]?[lr]-)" UI_DIRS --include=*.tsx | wc -l`, existing project rules about UI, existing hooks and CI, `PLATFORM` and, for iOS and Android separately, whether it has a public store listing, multi-brand signals (see 4b). **Version gate:** if Tailwind < 4, React < 19, or Next < 15 (app router), stop here and propose the upgrade first (`npx @tailwindcss/upgrade`, `npx @next/codemod@latest upgrade latest`, or the Vite/React upgrade), because shadcn rtl mode, `@theme` tokens and the logical-utility lint assume the current stack; setup continues only after the upgrade is committed and `PM build` passes. Verify required skills are available. Evidence: the report with the recorded names (`PLATFORM`, `TOKENS`, `SHELL`, `UI_DIRS`, `PM`, `DEV_CMD`).
2. **RTL infra.** With shadcn: set `"rtl": true` in components.json, run `PM dlx shadcn@latest migrate rtl`. Without: `PM dlx shadcn@latest init --rtl --base base --preset <name>`. **`--preset` is not optional in an unattended run:** CLI 4.21+ prompts for one and a non-TTY call simply HANGS with no output until it is killed. `nova` works; the `base-nova` that `-d` reports is rejected. In a repo that forbids `npx` (it has corrupted `node_modules` before), call the local `./node_modules/.bin/shadcn` instead and rewrite every generated `npx` invocation the CLI leaves behind, `.mcp.json` included. Ensure `<html lang="he" dir="rtl">` in `SHELL` and a DirectionProvider when on Base UI. The RTL gate itself is already in place and needs nothing installed: the global pre-commit hook scans the staged class strings on its own (see step 14a). `eslint-plugin-tailwind-rtl` is offered on top of it, never instead: try it once, and if it reports more than a handful of false positives, say so and drop it — on a Radix codebase it flags `side="left"` (a component API that flips itself) and the word "left" in an English test title, and its `--fix` writes `side="start"`, which Radix rejects; TherapyFlow measured 23 findings and 23 false positives. If it does earn its place: `PM add -D eslint-plugin-tailwind-rtl`, add `tailwindRtl.configs["recommended-tailwind"]` to the flat eslint.config (its rules are warnings, so every gate runs eslint with `--max-warnings=0`), run `npx eslint --fix --max-warnings=0 .` once here (the only whole-repo fix; later modes touch only their own files). **Requires a clean working tree**: if `git status` is not clean, stop and ask Nadav to commit or stash first, because a repo-wide autofix mixed into someone else's uncommitted work cannot be reviewed or reverted separately. Either way the project keeps a source-scanning guard of its own in `lint:ui`, because the hook only reads single lines and a class list can be split across several. This rewrites real layout classes across the app, so it is a visual change: screenshot the three busiest screens before and after, show both, and apply the visual change gate before committing; review the diff, anything inside a `dir="ltr"` element stays physical. Evidence: the physical-class count after, and `PM build` passing.
3. **Font.** One Hebrew family (Rubik or IBM Plex Sans Hebrew, subsets hebrew+latin) as `--font-sans` in `TOKENS`; Next: next/font; Vite: `@fontsource-variable/<family>` or self-hosted woff2 with `font-display: swap`. `--tracking-normal: 0`; max two families app-wide. This changes how every screen reads: screenshot two text-heavy screens before and after and apply the visual change gate. Evidence: `document.fonts` shows one family, plus the approved comparison.
4. **Tokens.** (a) House base first: copy `~/nadavai/templates/design/base.css` next to `TOKENS` as `base.css` and add `@import "./base.css";` right after the tailwind import; delete any project-level duplicates of what it defines (type scale, motion, z-index, safe-area vars, focus ring, reduced-motion rule) — except one that is load-bearing, which is the normal case for a z-index scale: an app's layering is usually the scar of a real stacking bug, and the house names collide with it silently because both sides are called `--z-*`. Keep the project's, drop only the names it does not use, and record the deviation in DESIGN.md with the bug that produced it. It is structure only; the app keeps its own colors, font and radius personality. (b) Audit `@theme` in `TOKENS`: colors count, OKLCH share, accents, dark mode. If no coherent theme: ask Nadav for a tweakcn preset name or a reference screenshot, then `npx shadcn@latest add https://tweakcn.com/r/themes/<name>.json`. Target: one accent, neutrals, three status colors, three radius values, 4px spacing, a `--ring` focus token, dark mode wired (`prefers-color-scheme`, or next-themes with `attribute="class"`). Replace stray hex in components with tokens. Tokens change colour across the whole app, so this is the largest visual change in setup: screenshot the three busiest screens before and after, in light and dark, show them side by side and apply the visual change gate per screen that shifted. Evidence: `grep -rE "#[0-9a-fA-F]{6}" UI_DIRS --include=*.tsx | wc -l` before/after, the approved comparisons, and a dark-mode screenshot.
4b. **Multi-brand check (always ask, never assume).** Look for signs of more than one brand/vertical/tenant: any `data-*` attribute used as a brand scope (`data-brand`, `data-vertical`, `data-tenant`, `data-theme` beyond light/dark — grep the attribute, not one spelling of it), theme switch code, multiple logo/color sets, route groups or build modes per vertical (e.g. clinic vs salon), and a second entry point in the bundler config. If found, ask Nadav with the recommended option first: "shared root + one file per vertical". On yes: `DESIGN.md` at root holds what is shared (type, spacing, radius, motion, RTL rules, states); `design/<vertical>/DESIGN.md` holds per-vertical color roles, tone, references; tokens in `TOKENS` scoped as `[data-brand="<vertical>"] { ... }` on top of the shared `@theme`; PRODUCT.md gets one section per vertical. From here on, every Impeccable critique/harden/document and every DoD run happens once per vertical (set the brand attribute via a query param or env for the DoD routes). `design/<vertical>/DESIGN.md` and a flat `design/<vertical>.md` are both accepted, and whichever the project already uses is the one to keep; the gap scan looks for either.

   **A second bundle is not a second theme.** When the vertical is its own build (a separate entry, a build mode, its own bundler output) rather than a scope on one document, it needs its own port, its own report directory, and a fixture in place of a QA login, because its identity is baked in at build time and there is nobody to log in as. Three things follow, none of them optional: `DOD_VERTICAL` in the DoD config (`dod-shared.ts`) so the products do not share a score; its build profile comes from an env seam, never from the committed real-tenant profile, so the fixture and the shipped app cannot swap places; and every dependency that the main app takes for granted is checked against that bundle, since a shared component drags its imports across the entry boundary — see the analytics rule in `~/nadavai/guides/posthog-init.md`.

10b. **Preview on invented data (a new app, only inside a task Nadav gave to build that app; or an existing app with no preview, only when Nadav asks for it from `plan` step 5; otherwise an existing app gets it as unit 1 of a redesign build plan he approved).** `shared/rules.md`, «An app is built once»: every screen built after this step is shown to Nadav playing in the preview, so it exists before the first screen. With the no-demo check (it fails when demo code or invented data is in a build users get: the web build; on Capacitor or Expo also the OTA bundle and each store build, as point 4 says who runs it) these are one script in the app repo, added as a step of the landing CI. Evidence: the preview running with the shell and the step 10 states, and each check failing on its planted case, then passing clean.
11. **Styleguide route (the one page that shows the whole system).** `app/(dev)/styleguide/page.tsx` or `src/routes/dev/styleguide.tsx`: renders every token group from `TOKENS` (colors as swatches with names, type scale, radii, spacing, shadows), every installed shadcn component in its states (default, hover, focus, disabled, loading, error) and the three state components from step 10, all RTL, in one long page with an in-page index. `noindex`, not linked from product navigation, present in dev and preview only (env or route group). 14. **Enforcement (rules that run without me).** (a) Pre-commit: nothing to install. Nadav's global `~/.git-hooks/pre-commit` (from nadavai) scans the staged class strings for physical direction utilities, then runs eslint `--max-warnings=0` and impeccable detect on the staged files of any repo whose package.json has `lint:ui`. The RTL scan is the hook's own and depends on no plugin, because until 17/09 it was eslint-plugin-tailwind-rtl's job and a project that declined that plugin silently had no commit-time gate at all while its rules file promised one. Never add husky or lefthook: husky rewrites `core.hooksPath` and silently disables the global commit-msg, pre-push and Cloudflare deploy hooks. If the project already has husky, move its commands into `package.json` scripts and remove it (ask first). Prove the gate, never assume it: stage a throwaway file containing `className="ml-4"`, run the hook, and show the rejection; then check the other direction by running the same scan over the whole of `UI_DIRS` and showing that it reports nothing, because a gate with false positives is a gate someone will switch off. Revert both. This step is a measurement, and it is what caught the hook passing `ml-4` on TherapyFlow. (b) CI step: install `~/nadavai/templates/ci/ui.yml` as `.github/workflows/ui.yml`, the nightly's input, and verify the rest, as `shared/rules.md`, «Where checks run», says. (c) PR template: copy `~/nadavai/templates/ci/PULL_REQUEST_TEMPLATE.md` to `.github/` and fill `{PM}`. (d) Lighthouse CI budget: `PM add -D @lhci/cli`, copy `~/nadavai/templates/ci/lighthouserc.json` to the root, fill `{PORT}` and `{START_CMD}` (`pnpm start` on Next after a build, `pnpm preview --port PORT` on Vite), add the product routes from `e2e/dod/routes.json` (never the styleguide), run `heavy-slot -- PM exec lhci autorun` once locally so the first numbers are known (from then on the nightly measures and reports it); if the project already has `lighthouse.yml`, merge and delete the old one — and `ls -a` for a `.lighthouserc*` dotfile while you are there: LHCI prefers it over the file you just wrote, so a stale one from an old launch keeps winning in silence and the report describes a config nobody has read in a year. TherapyFlow had one measuring the SPA shell twice. (e) `STATUS.md` (or BACKLOG.md, whichever the project uses): a "UI system" line with the date, the DoD scores and the styleguide route. Commit `chore(design): ui rules, gate and enforcement`. Evidence: the rejected test commit, the CI step found (or the request written), `git log -1`.
