# nadav-design

Mode is the first word of `$ARGUMENTS` (`setup`, `plan`, `screen`, `audit`, `redesign`, `ship`, `retro`, `next`). If empty or `next` (read-only): do not start a mode; run the gap scan (retro step 4b) and print, in Hebrew, where this project stands in the loop (derived from the **Setup artifacts** and **Loop position** rules below, never from a run log), and the next one to three commands with the reason. Nadav never has to remember the order.

## Hard rules (every mode)

- Before the first step of any mode, read `shared/rules.md` (next to this file): tempo, track, his words, the standard, looking at screenshots, where checks run; and `shared/platform.md`.
- **Track and reference.** A site that presents (portfolio, landing, showcase, film, 3D) is track `site`, a demo for a client is `client-demo`: read `tracks/<track>.md` first. When Nadav gave a reference ("like this", a link, a video, a screenshot), read `shared/reference.md` first and build that, never your own concept.
- Work **one step at a time**. A step ends with evidence (command output, file diff, or screenshot) shown to Nadav before the next step starts. Never merge steps, never assume a step passed (tempo: `shared/rules.md`).
- On any failure: stop, report what failed and why in Hebrew, wait (tempo: `shared/rules.md`).
- **Looking at screenshots.** Measure first, look second, several images in one turn, never an image twice: `shared/rules.md`, «Looking at screenshots» (`ui-check`, `dembrandt`, `tesseract`).
- **Visual change gate.** The moment anything a user could see changes (colors, font, spacing, radius, a moved or resized element, an icon, motion, a string, a state that renders differently), stop. Do not describe it in chat and move on. Show the before and after screenshot of the affected screen at 375 and 1440 and ask Nadav, with AskUserQuestion, what to do: keep it, change it, or revert it. This applies to changes a tool made on its own, not only to ones I chose: `eslint --fix`, `shadcn migrate rtl`, a token replacement, an Impeccable fix, a font swap. His answer is what continues, and it is written into the step's evidence. In `redesign` the app never changes and the demo is this gate: every round ends with CHANGES-<date>.md (before and after for every change) that Nadav answers keep, change or revert before the next round, and a change to something he approved that no answer or finding asks for is never made; it waits for him as a `need` (tempo: `shared/rules.md`).
- **No open debt, ever.** A finding that is not fixed now does not stay a sentence in chat. It becomes a decided line: fixed, or a `- [ ]` item in `docs/ui-audit/PLAN.md` with its priority, or written in DESIGN.md as a knowing exception with his approval. Before a step is ticked, every finding it produced carries one of those three. In `redesign` the three homes are in the output repo (fixed in the demo, a row in its DECISIONS-OPEN.md or plan, or a knowing exception in its BRIEF.md), because that mode never writes into the app repo.
- **No open question, ever.** A question that comes up mid-step is asked when it comes up, with AskUserQuestion and 2-4 concrete options, never parked for the summary and never answered by guessing. A step does not end while a question about it is open, and nothing that depends on the answer is built before it is recorded (a workflow agent, which cannot ask, leaves that part alone and returns it for the parent to ask at once) (tempo: `shared/rules.md`).
- Chat in Hebrew. Code, comments and commit messages in English.
- Hebrew RTL-first: logical properties only (`ms/me/ps/pe/start/end`), never `left/right`. Numbers, phones and Latin brand names in `dir="ltr"` islands.
- No new font, library or dependency without asking. Do not touch mock data or existing tests unless asked.
- Never run `/impeccable craft`, `bolder`, `overdrive` or `delight` on product screens. Impeccable is the reviewer, not the generator.
- If a required plugin or skill is missing, report it and stop; do not install. Required = everything `~/nadavai/setup.sh` installs (the `dependencies` of `plugins/nadavai/.claude-plugin/plugin.json`: impeccable, interfaces, intent, posthog, chrome-devtools-mcp, wondelai ux-design / product-innovation / product-strategy / metaskills, and the nadavai bundle itself with shadcn, emil-design-eng, review-animations, hebrew-*, argos-*). Check with `claude plugin list`. `review-animations` is user-invoked: Nadav types it, like the impeccable commands.
- Before starting, print the step checklist for the mode and tick it as you go. Every mode ends with three things, in this order: the ticked checklist with one evidence line per step written to `.omc/design-runs/<mode>-<YYYY-MM-DD>.md` (an evidence log for `retro`; untracked, so never the source of truth for position; `redesign` writes it to the output repo's `RUN-LOG.md` instead); the `next` gap scan (no network calls); and, as the very last line, `הבא: /ux-<mode> ...`, the next command in the loop for this project with one reason. Never end without it. `retro` itself runs only when Nadav types `/ux-retro`.
- **Quality bar: the highest threshold everywhere, in every project, new or existing.** Coverage first: the DoD measures **every route of the app** (generated by `e2e/dod/routes.mjs`, verified by its `--check`), never a sample; a score over a subset is not a score. It runs as the **QA account, which has access to everything**: no page is skipped for lack of permission, and a page the QA session cannot open reports as unreachable and forces the score to 0 until access is fixed. Any route still left out is named to Nadav with its reason. Where each check runs and what blocks: `shared/rules.md`, «Where checks run». DoD = 100, axe = 0 violations, Lighthouse from `lighthouserc.json` (performance, accessibility, best-practices and SEO all = 100, asserted on the median of 5 runs **taken on an idle machine** — Green Room measured a 3-5x spread in the performance score from machine load alone, so before any run, wait for 1-minute load average under ~7 and say what it was; a score measured under load is not reported at all, in either direction; this is the one machine-load rule. One invocation everywhere: `PM exec lhci autorun`, the pinned devDependency. LCP <= 2.0s, CLS <= 0.05, TBT <= 150ms, TTI <= 3s; field INP < 200ms from PostHog web-vitals), `lint:ui` = 0 findings, console clean. The gated numbers live only in `~/nadavai/templates/ci/lighthouserc.json` and `templates/dod/e2e/dod/dod-shared.ts` (axe is part of the DoD score); field INP is reported from PostHog, not gated. This file quotes them. A threshold is never lowered or ignored to pass: the code is fixed, or the step stops and the gap is reported with its cause; nothing merges with it. In `screen` and `ship`, fixes go to the standard of the reviewer, not "good enough".
- **Setup artifacts (defined once; audit step 1, ship step 0, retro 4b and the session hook all mean this list):** `DESIGN.md` (with the Foundations section), `PRODUCT.md` (with Voice), `.claude/rules/ui.md`, the CLAUDE.md line, `base.css` imported by `TOKENS`, the styleguide route, `e2e/dod/` + `playwright.dod.config.ts` + the `dod` script, `lighthouserc.json`, the CI step (`shared/rules.md`, «Where checks run»), `.github/PULL_REQUEST_TEMPLATE.md`, the `lint:ui` script, a pre-commit hook running it, the accessibility page (and the privacy page when personal data is collected), and, per vertical when multi-brand, `design/<vertical>/DESIGN.md` or the flat `design/<vertical>.md` — either spelling counts as present.
- **Loop position (derived from tracked files only):** setup done = `.claude/rules/ui.md` + `e2e/dod/` + the CI step + `lighthouserc.json` exist; plan done = `docs/specs/<feature>.md` exists; screens left = unchecked `- [ ]` items under "Screens" in `docs/specs/*.md` and in `docs/ui-audit/PLAN.md`; audit done = `docs/ui-audit/PLAN.md` exists (new projects: due once 4-5 screens are ticked and no PLAN.md exists yet); ship done = the `UI system` line in STATUS.md (or BACKLOG.md) contains the literal word `released` followed by a date, exactly as ship step 9 writes it. The date alone means nothing: **setup step 14(e) writes a dated `UI system` line of its own**, so a rule that reads for a date reports `ship` as done on every project that has only finished setup. Green Room carried such a line from 17/09 and had never run `ship`. Redesign = the output repo `~/design-redesign/<app repo folder name>/` (or the path Nadav gives) holding `redesign.json`: in progress until its `plan/build-plan.md` has the line `Status: OWNER-APPROVED answer <N> commit <sha>` (the token, nothing else on the line; `Status: DRAFT` before); units left = rows of that plan's Units table whose State is not `done`. The evidence log under `.omc/design-runs/` only adds detail when present.
- Projects are Next.js (app router) or Vite + React, often wrapped by Capacitor; SporChat's native app is Expo. Step 1 of `setup` records the project shape and every later step uses these names: `PLATFORM` (`shared/platform.md`), `TOKENS` (the token CSS file: `app/globals.css`, `src/index.css` or `src/globals.css`), `SHELL` (`app/layout.tsx`, or `index.html` + `src/main.tsx`), `UI_DIRS` (`app/ components/` or `src/`), `PM` (from the lockfile), `DEV_CMD` and port. Never assume Next paths on a Vite project.

## Modes

Each mode is one file. Read the Hard rules above, then the file of the mode, and follow it from its first
step (step 0 where it has one). Never run a mode from memory of this table.

| Mode | File |
|---|---|
| Mode `setup` (one time per project) | `modes/setup.md` |
| Mode `audit` (deep, every screen, no fixes) | `modes/audit.md` |
| Mode `redesign` (the whole app, demo first, no app code) | `modes/redesign.md` |
| Mode `screen <name>` (one screen, new or redesign) | `modes/screen.md` |
| Mode `plan <feature>` (before any code, one feature) | `modes/plan.md` |
| Mode `ship` (before release and after) | `modes/ship.md` |
| Mode `retro` (after a run; improves this skill, never the project) | `modes/retro.md` |
| `next` (or no argument) | the first paragraph of this file, with retro step 4b in `modes/retro.md` |

## Which mode when

**Existing project:** `setup` (step 0 clean slate) → `retro` → `audit` → Nadav approves `docs/ui-audit/PLAN.md` → `screen <name>` in PLAN order (shared first, then critical) → `ship` → `retro` → after launch: `plan <feature>` → `screen` per screen; `ship` step 8 weekly.

**Existing project whose whole look changes:** `setup` → `redesign` (brief, demo, decisions, rounds, plan) → START-BUILD in a build session → `screen <name>` per plan unit → `ship` → `retro`.

**New project:** `shadcn create --rtl` → `setup` (step 11b direction pick) → `retro` → `plan <feature>` → `screen <name>` per screen from the plan → `audit` after 4-5 screens → `screen` for the fixes → `ship` → `retro` → launch.

**A site or a client demo:** with a reference, `REFERENCE.md` first → `setup` when it has a framework (no 11b) → the order of work in `tracks/site.md` or `tracks/client-demo.md` → `ship`.

`next` (or no argument) tells Nadav where the project is in this order and what to run. `retro` after every run, so the skill learns from each project.
