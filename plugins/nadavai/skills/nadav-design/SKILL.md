# nadav-design

Mode is the first word of `$ARGUMENTS` (`setup`, `plan`, `screen`, `audit`, `ship`, `retro`). If empty, ask which mode in one line and stop.

## Hard rules (every mode)

- Work **one step at a time**. A step ends with evidence (command output, file diff, or screenshot) shown to Nadav before the next step starts. Never merge steps, never assume a step passed.
- On any failure: stop, report what failed and why in Hebrew, wait.
- Chat in Hebrew. Code, comments and commit messages in English.
- Hebrew RTL-first: logical properties only (`ms/me/ps/pe/start/end`), never `left/right`. Numbers, phones and Latin brand names in `dir="ltr"` islands.
- No new font, library or dependency without asking. Do not touch mock data or existing tests unless asked.
- Never run `/impeccable craft`, `bolder`, `overdrive` or `delight` on product screens. Impeccable is the reviewer, not the generator.
- If a required plugin or skill is missing, report it and stop; do not install. Required: impeccable, shadcn, emil-design-eng, review-animations, hebrew-tailwind-preset, hebrew-rtl-best-practices, argos-cli, web-quality-skills.
- Before starting, print the step checklist for the mode and tick it as you go. Every mode ends by writing the ticked checklist with one evidence line per step to `.omc/design-runs/<mode>-<YYYY-MM-DD>.md` and then running `retro` steps 0-5 automatically in short form (findings and proposals only, nothing applied); the full `/ux-retro` is for when Nadav wants the edits applied.
- **Quality bar: the highest threshold everywhere, in every project, new or existing.** DoD = 100, axe = 0 violations, Addy a11y = 100, Lighthouse from `lighthouserc.json` (performance >= 0.95, accessibility, best-practices and SEO = 1, LCP <= 2.0s, CLS <= 0.05, TBT <= 150ms), `lint:ui` = 0 findings, console clean. A threshold is never lowered or ignored to pass: the code is fixed, or the gap is reported with its cause and left open. In `screen` and `ship`, fixes go to the standard of the reviewer, not "good enough".
- Projects are Next.js (app router) or Vite + React, often wrapped by Capacitor/TWA. Step 1 of `setup` records the project shape and every later step uses these names: `TOKENS` (the token CSS file: `app/globals.css`, `src/index.css` or `src/globals.css`), `SHELL` (`app/layout.tsx`, or `index.html` + `src/main.tsx`), `UI_DIRS` (`app/ components/` or `src/`), `PM` (from the lockfile), `DEV_CMD` and port. Never assume Next paths on a Vite project.

## Mode `setup` (one time per project)

0. **Clean slate (existing projects only; skip on a fresh `shadcn create`).** Before anything else, find every trace of an older design/skill/memory system so nothing overlaps with the new stack. Inventory only, no deletion yet:
   - Project agent config: `.claude/skills/*`, `.claude/commands/*`, `.claude/agents/*`, `.agents/skills/*`, `.cursor/rules/*`, `.codex/*`, `skills-lock.json`, hooks in `.claude/settings.json` / `.claude/settings.local.json` that mention design, ui, ux, taste, guard, lint-motion, impeccable, superdesign, stitch, pro-max.
   - Design docs and state: `DESIGN.md`, `design.md`, `PRODUCT.md`, `design-system.md`, `style-guide.md`, `tokens.json`, `design-plans/`, `.impeccable/`, `.superdesign/`, `superdesign/`, `.stitch/`, `.design/`, `docs/design*`, `docs/ui-audit/`, `.omc/skills/*design*`, `.omc/plans/*design*`, design entries in `.omc/notepad.md` and `.omc/project-memory.json`.
   - Rules text: sections in `CLAUDE.md` and `AGENTS.md` about design, UI, fonts, colors, motion, RTL from the old system.
   - Never touch product code (app/, components/, lib/, styles) in this step; tokens and CSS are handled in steps 2-4.
   - **Mechanical sweep, so nothing is missed.** Run and show the results of:
     `git ls-files -co --exclude-standard | grep -viE "^(node_modules|\.next|dist|build|public/fonts)/" | grep -iE "design|ui-ux|uiux|taste|impeccable|superdesign|stitch|pro-?max|brandkit|mockup|wireframe|style-?guide|tokens?\.(json|md)|prd|spec-design|nadav-(design|qa|fidelity)|ux-doctrine|polish-journey|previsual|live-design|decision-page|prompt-spec|\.claude/|\.agents/|\.cursor/|\.codex/|\.omc/skills|\.omc/plans"` (file names), and
     `grep -rilE "impeccable|superdesign|ui-ux-pro-max|taste-skill|gpt-taste|design-taste|redesign-existing|nadav-design|nadav-qa|ux-doctrine|polish-journey|live-design-lab|mockup-to-app|DESIGN-CONSTITUTION|design system rules|design tokens" --include=*.md --include=*.json --include=*.mdc --include=*.txt --include=*.html --exclude-dir=node_modules --exclude-dir=.next --exclude-dir=.git .` (file contents). Add every hit to the inventory unless it is product code or a product asset.
   Show the full list with paths and one line on what each is. Ask Nadav to approve. Then: move everything approved to `.omc/archive/design-legacy-<YYYY-MM-DD>/` (keep paths, write `MANIFEST.md`), remove the old sections from CLAUDE.md/AGENTS.md/README (keep non-design rules), remove the matching hooks and settings entries, delete design entries from `.omc/notepad.md` and `.omc/project-memory.json`, and commit `chore(design): archive legacy design system before setup`.
   **Verification (mandatory):** re-run both sweeps; the only allowed hits are files this skill creates later (`DESIGN.md`, `PRODUCT.md`, `docs/specs/`, `docs/ui-audit/`, `e2e/dod*`, `.omc/archive/`). Anything else: back to the inventory. Evidence: the two empty sweep outputs, the manifest, `git status` clean. Only after this, step 1.

1. **Detect.** Read CLAUDE.md, package.json, the lockfile, components.json (if any), `TOKENS`, `SHELL`, `.claude/rules/*`, `.github/workflows/*`, `.husky/` or `lefthook.yml`, `capacitor.config.*`, `public/manifest*`. Report: framework family (Next or Vite) + version, Tailwind version, shadcn yes/no and base, current font, `dir="rtl"` on `<html>` yes/no, count of physical direction classes: `grep -rE "\b(ml|mr|pl|pr|left|right|text-left|text-right|rounded-[lr])-" UI_DIRS --include=*.tsx | wc -l`, existing project rules about UI, existing hooks and CI, mobile shell (Capacitor / TWA / PWA manifest) yes/no, multi-brand signals (see 4b). **Version gate:** if Tailwind < 4, React < 19, or Next < 15 (app router), stop here and propose the upgrade first (`npx @tailwindcss/upgrade`, `npx @next/codemod@latest upgrade latest`, or the Vite/React upgrade), because shadcn rtl mode, `@theme` tokens and the logical-utility lint assume the current stack; setup continues only after the upgrade is committed and `PM build` passes. Verify required skills are available. Evidence: the report with the recorded names (`TOKENS`, `SHELL`, `UI_DIRS`, `PM`, `DEV_CMD`).
2. **RTL infra.** With shadcn: set `"rtl": true` in components.json, run `PM dlx shadcn@latest migrate rtl`. Without: `PM dlx shadcn@latest init --rtl --base base`. Ensure `<html lang="he" dir="rtl">` in `SHELL` and a DirectionProvider when on Base UI. `PM add -D eslint-plugin-tailwind-rtl`, add `tailwindRtl.configs.recommended` to eslint.config, run `npx eslint --fix .`; review the diff, anything inside a `dir="ltr"` element stays physical. Evidence: the physical-class count after, and `PM build` passing.
3. **Font.** One Hebrew family (Rubik or IBM Plex Sans Hebrew, subsets hebrew+latin) as `--font-sans` in `TOKENS`; Next: next/font; Vite: `@fontsource-variable/<family>` or self-hosted woff2 with `font-display: swap`. `--tracking-normal: 0`; max two families app-wide. Evidence: `document.fonts` shows one family.
4. **Tokens.** (a) House base first: copy `~/nadavai/templates/design/base.css` next to `TOKENS` as `base.css` and add `@import "./base.css";` right after the tailwind import; delete any project-level duplicates of what it defines (type scale, motion, z-index, safe-area vars, focus ring, reduced-motion rule). It is structure only; the app keeps its own colors, font and radius personality. (b) Audit `@theme` in `TOKENS`: colors count, OKLCH share, accents, dark mode. If no coherent theme: ask Nadav for a tweakcn preset name or a reference screenshot, then `npx shadcn@latest add https://tweakcn.com/r/themes/<name>.json`. Target: one accent, neutrals, three status colors, three radius values, 4px spacing, a `--ring` focus token, dark mode wired (`prefers-color-scheme`, or next-themes with `attribute="class"`). Replace stray hex in components with tokens. Evidence: `grep -rE "#[0-9a-fA-F]{6}" UI_DIRS --include=*.tsx | wc -l` before/after, and a dark-mode screenshot.
4b. **Multi-brand check (always ask, never assume).** Look for signs of more than one brand/vertical/tenant: `data-brand`, `data-theme` beyond light/dark, `[data-tenant]`, theme switch code, multiple logo/color sets, route groups or build modes per vertical (e.g. clinic vs salon). If found, ask Nadav with the recommended option first: "shared root + one file per vertical". On yes: `DESIGN.md` at root holds what is shared (type, spacing, radius, motion, RTL rules, states); `design/<vertical>/DESIGN.md` holds per-vertical color roles, tone, references; tokens in `TOKENS` scoped as `[data-brand="<vertical>"] { ... }` on top of the shared `@theme`; PRODUCT.md gets one section per vertical. From here on, every Impeccable critique/harden/document and every DoD run happens once per vertical (set `data-brand` via a query param or env for the DoD routes). Evidence: the file tree and one screenshot per vertical.

5. **PRODUCT.md.** Run `/impeccable init`. First run: approve the launcher with "always allow". Answer from the repo, mark guesses as inferred, ask Nadav only what cannot be inferred. Add the line: "Hebrew RTL-first. Logical properties only. Numbers and Latin names in dir=ltr islands." Then make sure it has a **Voice** section (add it if `init` did not): form of address (neutral Hebrew when the reader's gender is unknown, or the product's chosen form), tone in three adjectives, a glossary of 5-10 core terms with the one Hebrew word each, date/number/currency format (`he-IL`). If Nadav wants help with the voice: `/intent:articulate`. Evidence: file exists, Voice section present, Nadav approved it.
6. **DESIGN.md.** Run `/impeccable document`; merge the sections of `~/nadavai/templates/design/DESIGN-base.md` into it under "Foundations" (the app's own sections stay above them); then `npx @google/design.md lint DESIGN.md` until 0 errors. `TOKENS` is the source of truth; DESIGN.md describes it. Evidence: lint output.
7. **Rules layer (so every future session obeys without being told).** (a) Append to the project CLAUDE.md: `Before any UI work read DESIGN.md and PRODUCT.md. Use only tokens from TOKENS. Hebrew RTL-first, logical properties only. Every list has empty/loading/error states. Project UI rules: .claude/rules/ui.md.` (b) Copy `~/nadavai/templates/ui-rules/ui.md` to `.claude/rules/ui.md`, fill `{UI_GLOB}`, `{TOKENS}`, `{PM}`, `{PM_DLX}`. (c) If an older project rule already covers UI (e.g. `.claude/rules/rtl-design.md`): delete from it every line the new file covers and every stale fact (old hex, old font, mockup paths), keep only product-specific behaviour rules, and say what was removed. (d) `AGENTS.md` stays a symlink to CLAUDE.md. Evidence: the three diffs.
8. **shadcn MCP.** `npx shadcn@latest mcp init --client claude`; ensure `.mcp.json` has `"type": "stdio"`. Evidence: file content.
9. **Mobile shell (TWA / WebView / Capacitor / PWA).** Nadav ships web apps inside Android TWA, WebView or Capacitor, so the shell is part of setup, not a later fix. In `SHELL`: `viewport-fit=cover`, `theme-color` for light and dark, `color-scheme`. Apply the base.css vars (`--safe-top/--safe-bottom/--safe-start/--safe-end`) to the app shell, sticky headers and bottom bars; `dvh` instead of `vh` everywhere. Manifest (`app/manifest.ts` or `public/manifest.webmanifest`): Hebrew name, `lang: he`, `dir: rtl`, `display: standalone`, icons 192/512 + maskable, theme/background colors from tokens. With Capacitor: follow the `capacitor-app-development` skill for edge-to-edge and safe areas on Android, and `capacitor-plugins` for StatusBar, SplashScreen, Keyboard (so inputs are not covered) and the Android back-button handler. With TWA: `public/.well-known/assetlinks.json` (SHA-256 of the signing key; placeholder if unknown) and a service worker that serves an offline page, because Chrome's TWA quality criteria require installability and an offline response. Offline: a fallback page or a clear offline state (mobile-native skill). Evidence: Chrome DevTools MCP emulation of a 360-wide phone with a notch, screenshot of the shell with a keyboard-focused input, manifest passes the PWA checks of `web-quality-skills`.
10. **Foundations (shared code every screen relies on; built once, before any screen).** Next: `app/error.tsx`, `app/global-error.tsx`, `app/not-found.tsx`, `app/loading.tsx` in Hebrew on the tokens. Vite: a root ErrorBoundary, a not-found route, a route-level suspense fallback. Ask before adding a dependency that is not already in package.json (zod, react-hook-form, sonner, lucide are usually there). Evidence: `PM build` passes; screenshots of the error, not-found, empty and loading states.
11. **Styleguide route (the one page that shows the whole system).** `app/(dev)/styleguide/page.tsx` or `src/routes/dev/styleguide.tsx`: renders every token group from `TOKENS` (colors as swatches with names, type scale, radii, spacing, shadows), every installed shadcn component in its states (default, hover, focus, disabled, loading, error) and the three state components from step 10, all RTL, in one long page with an in-page index. `noindex`, not linked from product navigation, present in dev and preview only (env or route group). Add it to the DoD routes. Why: DoD and Argos snapshot the entire system in one run, Claude Design syncs from a real page, and the general redesign later is judged on this page first. Evidence: screenshots of the page at 375 and 1440, light and dark.
11b. **Direction pick (only on a fresh project, or when Nadav says he wants a new look; never assumed).** Prepare three candidate themes that differ in accent, neutrals, radius and font (from Rubik / IBM Plex Sans Hebrew / Assistant): tweakcn presets or hand-tuned, each scoped as `[data-candidate="a|b|c"]` on top of the house base. Screenshot the styleguide page under each at 375 and 1440, light and dark. Show Nadav the three side by side with one line on the intent of each; he picks. Apply the winner into `TOKENS`, delete the other two scopes, re-run `/impeccable document` and the lint. Never pick for him, never blend candidates. Evidence: the six screenshots and the diff.

Set `e2e/dod/routes.json` to the 3-6 main screens + the styleguide route + one `?state=empty` and one `?state=error` route if the app supports them; set `DEV_CMD` and the port in the config; add script `"dod": "playwright test -c playwright.dod.config.ts"`; `PM add -D @playwright/test @axe-core/playwright` when missing; `PM exec playwright install chromium`; ignore `/reports/` and `/test-results/`. Run on a free port. Evidence: `reports/dod/dod.json` score per route.

(b) Argos: `PM add -D @argos-ci/playwright`, wrap the DoD screenshots with `argosScreenshot`, add the reporter to `playwright.dod.config.ts`; leave `ARGOS_TOKEN` for CI (ask, never create accounts). (c) Accessibility statement: create the page (`app/accessibility/page.tsx` or the Vite route) as a Hebrew skeleton per the israeli-accessibility-compliance skill, and a privacy page skeleton next to it if the app collects personal data; link both from the footer. (d) Add `"lint:ui": "eslint . && npx impeccable@latest detect UI_DIRS"` to package.json (locally the plugin launcher is newer; CI uses the npm package). Evidence: the four diffs. Skip (a)/(b) with "not now" if Nadav says so; never skip (c)/(d).
14. **Enforcement (rules that run without me).** (a) Pre-commit: with the existing husky/lefthook, else `PM add -D husky && PM exec husky init`; the hook runs `PM lint:ui` (eslint with tailwind-rtl + impeccable detect) on every commit; prove it by trying to commit a file with `ml-4` and showing the rejection, then reverting. End with a table: step, what was done, evidence, what remains.

## Mode `audit` (deep, every screen, no fixes)

This is the full preparation Nadav wants on an existing project before any renovation starts. Cover every screen, not only the main one.

1. Confirm setup exists (DESIGN.md, PRODUCT.md, `.claude/rules/ui.md`, `e2e/dod/`). If not, say "run `/nadav-design setup` first" and stop.
2. **Inventory.** List every route (Next: `find app -name page.tsx`; Vite: the router file), every shared layout, and every component under components/ with its usage count. Mark screens as critical (auth, signup, onboarding, checkout, payment, account) or normal. Save to `docs/ui-audit/INVENTORY.md`. Evidence: the file.
3. **Per screen, in inventory order** (one screen per step, evidence after each): `/impeccable critique`; screenshots at 375 and 1440, light and dark, RTL; note visible issues. For critical screens also `/interfaces:interface-review`. Append findings to `docs/ui-audit/<route-slug>.md`.
4. **Codebase-wide.** `npx impeccable detect UI_DIRS`; `npx eslint . ` (tailwind-rtl rule count); `grep` for stray hex colors, physical direction classes, `transition: all`, fonts loaded; `/improve-animations` (Emil, read-only) if any motion exists. Evidence: counts and the report paths.
5. **Measurement.** web-quality-skills audit on every route in `e2e/dod/routes.json` via Chrome DevTools MCP; `pnpm dod` on all routes. Evidence: reports.
6. **Tokens vs reality.** Compare DESIGN.md tokens with what screens actually use; list drift (colors, radii, fonts, spacing outside the scale). Evidence: the list.
7. **Renovation plan.** Write `docs/ui-audit/PLAN.md`: per screen a P0-P3 list with file:line, the recommended order of `/nadav-design screen <name>` runs (critical + most P0 first), what is shared (fix once in components/ before screens), and an estimate per screen. Show it to Nadav and stop. Nothing is fixed in this mode.

## Mode `screen <name>` (one screen, new or redesign)

1. **Brief.** Write a 10-line brief for the screen: purpose, user, data source, and every state (loading, empty, error, success), acceptance: RTL, 375 and 1440, dark mode, keyboard, touch targets >= 44px, reduced-motion, real Hebrew copy, tokens only. Show it; wait for OK.
2. **Build or redesign** with shadcn components only (add via `PM dlx shadcn@latest add <name>`), tokens from globals.css, logical properties. For a redesign: keep behavior, strings, routes and data code unchanged.
3. `/impeccable critique` on the screen; apply the P0/P1 findings.
4. `/impeccable harden` (edge cases, long text, RTL, states).
5. If the screen has motion: `/review-animations`; apply the Block items.
5b. **Second opinion, only when the screen is critical** (auth, signup, onboarding, checkout, payment, account deletion) or introduces a new complex component: `/interfaces:interface-review` on the working tree; apply HIGH findings. For a new complex component also `/interfaces:break` and fix what breaks. Otherwise skip this step and say "skipped: not critical".
6. `npx impeccable detect UI_DIRS` clean; `npx eslint --fix .` clean; then the Vercel web-design-guidelines skill as a static lint on the changed files (a11y, forms, focus, animation, Intl), and `vercel-react-best-practices` + `vercel-composition-patterns` on the same files (waterfalls, bundle, memo, composition); fix the findings or explain each one left.
7. `PM dod` (add the route to `e2e/dod/routes.json`). Score must be 100 or every deduction explained.
8. Screenshots at 375 and 1440, light and dark, RTL. Look at them; fix anything visibly wrong.
9. Commit with Conventional Commits. Report: score, screenshots paths, what changed, what was left out. Ask before starting another screen.

Optional after a critical screen, only if Nadav asks: `/interfaces:interface-review`, `/interfaces:break`.

## Mode `plan <feature>` (before any code, one feature)

0. **Is the problem clear?** If the problem, audience or whether to build at all is unclear: `/intent:strategize` and `/intent:investigate` (ember) first; if user research already exists: `synthesize-research` (nadavai) before the PRD; if Nadav is about to interview users: the `mom-test` skill (wondelai) shapes the questions. Otherwise say "problem clear" and continue. Evidence: the brief or the one line.
1. **PRD.** `/write-spec` (bundled in the nadavai plugin) for the feature; answer its questions from the repo and PRODUCT.md, ask Nadav only what cannot be inferred. Save to `docs/specs/<feature>.md`. Evidence: the file, Nadav approved.
2. **Job.** `jobs-to-be-done` skill (wondelai product-innovation): one job statement per user type, saved into the same spec under "Jobs". Evidence: the section.
3. **Flows and IA.** Intent plugin (wren): `/intent:journey` for the end-to-end flow, `/intent:organize` for IA and navigation, `/intent:wireframe` for the screen structure, `/intent:localize` for the RTL and Hebrew notes. Output as Mermaid in `docs/specs/<feature>.md` under "Flows": happy path plus two failure paths, every decision node has an exit. Evidence: the Mermaid renders.
4. **Heuristics pre-check.** `ux-heuristics` skill (wondelai ux-design) on the planned flow, reading `references/cultural-ux.md` for the RTL section. If the feature is a funnel (landing, signup, checkout, onboarding): the `conversion-optimization` skill (wondelai) on the planned flow as well. Then `/intent:evaluate` (vigil) on the wireframes: Nielsen, anti-patterns, WCAG 2.2, and `/intent:fortify` for edge cases, empty and error states, offline. Fold findings into the spec. Evidence: the findings list.
5. **Mockup.** If Nadav wants to see it before code: `/design-sync` once (if not done), then `/design` for a low-fi canvas of the key screen, or hand him the spec to open in Claude Design. Evidence: canvas link or "skipped by Nadav".
6. **Hand off.** `/intent:specify` (rune): per-screen spec with behaviour, states, copy and accessibility, saved under "Screens" in the same file; then list the screens to build, each becomes a `/nadav-design screen <name>` run. Ask which first.

## Mode `ship` (before release and after)

0. **Pre-flight.** All of these exist or stop with the missing list: `DESIGN.md`, `PRODUCT.md` (with Voice), `.claude/rules/ui.md`, `e2e/dod/`, the styleguide route, the accessibility page, `.github/workflows/ui.yml`. `git status` clean, `PM build` passes, and if `docs/ui-audit/PLAN.md` exists every P0 in it is closed. Evidence: the checklist.

## Mode `retro` (after a run; improves this skill, never the project)

0. Find the run: the newest `.omc/design-runs/*.md` (or ask Nadav to paste the checklist if it was not written), plus `git log --since` its date, `reports/dod/dod.json`, `.lighthouseci/` or the Lighthouse CI output, `docs/ui-audit/`, `.omc/notepad.md`. Evidence: the list of sources found.
1. **Step audit.** For every step of the mode that ran, one row: done with evidence / done without evidence / batched with another step / skipped / failed, with the line that proves it. "Done without evidence" and "batched" are failures of this skill, not of the project.
2. **Threshold audit.** DoD, axe, Addy, Lighthouse, `lint:ui`: met or not, and whether any threshold was lowered (`diff` the project's `lighthouserc.json` and `e2e/dod/` against `~/nadavai/templates/`). A lowered threshold is a P0 finding.
3. **Tool audit.** Every skill, plugin, template or command that was missing, errored, needed a permission prompt, was outdated (`npx` version vs plugin version) or produced output that was not used. Time per step when known.
4. **Question audit.** Questions asked that the repo already answered (breaks Nadav's rule), and decisions taken silently that should have been asked.
4b. **What Nadav has not done yet (the gap scan; retro proposes it without being asked).** Check the project against the whole loop, not only the mode that ran: setup files present (`DESIGN.md`, `PRODUCT.md` with Voice, `.claude/rules/ui.md`, `base.css` imported, styleguide route, `e2e/dod/`, `lighthouserc.json`, `ui.yml`, accessibility + privacy pages); `.omc/design-runs/` shows which modes never ran; `docs/ui-audit/PLAN.md` items still open; routes in the app missing from `e2e/dod/routes.json`; screens changed since the last `screen` run (`git log` on `UI_DIRS`) without a DoD run; a `ship` older than the last release tag; the weekly PostHog review overdue; multi-brand verticals without their own `design/<vertical>/DESIGN.md`. ## Which mode when

`setup` once per project → `plan <feature>` per feature → `screen <name>` per screen → `audit` any time you want a map without changes → `ship` before release and once after launch → `retro` after every run, so the skill learns from each project.
