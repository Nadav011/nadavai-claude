# nadav-design

Mode is the first word of `$ARGUMENTS` (`setup`, `plan`, `screen`, `audit`, `ship`, `retro`, `next`). If empty or `next` (read-only): do not start a mode; run the gap scan (retro step 4b) and print, in Hebrew, where this project stands in the loop (derived from the **Setup artifacts** and **Loop position** rules below, never from a run log), and the next one to three commands with the reason. Nadav never has to remember the order.

## Hard rules (every mode)

- Work **one step at a time**. A step ends with evidence (command output, file diff, or screenshot) shown to Nadav before the next step starts. Never merge steps, never assume a step passed.
- On any failure: stop, report what failed and why in Hebrew, wait.
- **Visual change gate.** The moment anything a user could see changes (colors, font, spacing, radius, a moved or resized element, an icon, motion, a string, a state that renders differently), stop. Do not describe it in chat and move on. Show the before and after screenshot of the affected screen at 375 and 1440 and ask Nadav, with AskUserQuestion, what to do: keep it, change it, or revert it. This applies to changes a tool made on its own, not only to ones I chose: `eslint --fix`, `shadcn migrate rtl`, a token replacement, an Impeccable fix, a font swap. His answer is what continues, and it is written into the step's evidence.
- **No open debt, ever.** A finding that is not fixed now does not stay a sentence in chat. It becomes a decided line: fixed, or a `- [ ]` item in `docs/ui-audit/PLAN.md` with its priority, or written in DESIGN.md as a knowing exception with his approval. Before a step is ticked, every finding it produced carries one of those three.
- **No open question, ever.** A question that comes up mid-step is asked when it comes up, with AskUserQuestion and 2-4 concrete options, never parked for the summary and never answered by guessing. A step does not end while a question about it is open.
- Chat in Hebrew. Code, comments and commit messages in English.
- Hebrew RTL-first: logical properties only (`ms/me/ps/pe/start/end`), never `left/right`. Numbers, phones and Latin brand names in `dir="ltr"` islands.
- No new font, library or dependency without asking. Do not touch mock data or existing tests unless asked.
- Never run `/impeccable craft`, `bolder`, `overdrive` or `delight` on product screens. Impeccable is the reviewer, not the generator.
- If a required plugin or skill is missing, report it and stop; do not install. Required = everything `~/nadavai/setup.sh` installs (the `dependencies` of `plugins/nadavai/.claude-plugin/plugin.json`: impeccable, interfaces, intent, posthog, chrome-devtools-mcp, wondelai ux-design / product-innovation / product-strategy / metaskills, and the nadavai bundle itself with shadcn, emil-design-eng, review-animations, hebrew-*, argos-*). Check with `claude plugin list`. `review-animations` is user-invoked: Nadav types it, like the impeccable commands.
- Before starting, print the step checklist for the mode and tick it as you go. Every mode ends with three things, in this order: the ticked checklist with one evidence line per step written to `.omc/design-runs/<mode>-<YYYY-MM-DD>.md` (an evidence log for `retro`; untracked, so never the source of truth for position); the `next` gap scan (no network calls); and, as the very last line, `הבא: /ux-<mode> ...`, the next command in the loop for this project with one reason. Never end without it. `retro` itself runs only when Nadav types `/ux-retro`.
- **Quality bar: the highest threshold everywhere, in every project, new or existing.** Coverage first: the DoD measures **every route of the app** (generated by `e2e/dod/routes.mjs`, verified by its `--check`), never a sample; a score over a subset is not a score. It runs as the **QA account, which has access to everything**: no page is skipped for lack of permission, and a page the QA session cannot open reports as unreachable and forces the score to 0 until access is fixed. Any route still left out is named to Nadav with its reason. DoD = 100 (CI fails below it), axe = 0 violations, Lighthouse from `lighthouserc.json` (performance, accessibility, best-practices and SEO all = 100, asserted on the median of 5 runs, LCP <= 2.0s, CLS <= 0.05, TBT <= 150ms, TTI <= 3s; field INP < 200ms from PostHog web-vitals), `lint:ui` = 0 findings, console clean. The gated numbers live only in `~/nadavai/templates/ci/lighthouserc.json` and `templates/dod/e2e/dod/dod-shared.ts` (axe is part of the DoD score); field INP is reported from PostHog, not gated. This file quotes them. A threshold is never lowered or ignored to pass: the code is fixed, or the step stops and the gap is reported with its cause; nothing merges with it. In `screen` and `ship`, fixes go to the standard of the reviewer, not "good enough".
- **Setup artifacts (defined once; audit step 1, ship step 0, retro 4b and the session hook all mean this list):** `DESIGN.md` (with the Foundations section), `PRODUCT.md` (with Voice), `.claude/rules/ui.md`, the CLAUDE.md line, `base.css` imported by `TOKENS`, the styleguide route, `e2e/dod/` + `playwright.dod.config.ts` + the `dod` script, `lighthouserc.json`, `.github/workflows/ui.yml` (with the DoD score gate), `.github/PULL_REQUEST_TEMPLATE.md`, the `lint:ui` script, a pre-commit hook running it, the accessibility page (and the privacy page when personal data is collected), and, per vertical when multi-brand, `design/<vertical>/DESIGN.md` or the flat `design/<vertical>.md` — either spelling counts as present.
- **Loop position (derived from tracked files only):** setup done = `.claude/rules/ui.md` + `e2e/dod/` + `.github/workflows/ui.yml` + `lighthouserc.json` exist; plan done = `docs/specs/<feature>.md` exists; screens left = unchecked `- [ ]` items under "Screens" in `docs/specs/*.md` and in `docs/ui-audit/PLAN.md`; audit done = `docs/ui-audit/PLAN.md` exists (new projects: due once 4-5 screens are ticked and no PLAN.md exists yet); ship done = the dated `UI system` line in STATUS.md (or BACKLOG.md) carries a release date. The evidence log under `.omc/design-runs/` only adds detail when present.
- Projects are Next.js (app router) or Vite + React, often wrapped by Capacitor/TWA. Step 1 of `setup` records the project shape and every later step uses these names: `TOKENS` (the token CSS file: `app/globals.css`, `src/index.css` or `src/globals.css`), `SHELL` (`app/layout.tsx`, or `index.html` + `src/main.tsx`), `UI_DIRS` (`app/ components/` or `src/`), `PM` (from the lockfile), `DEV_CMD` and port. Never assume Next paths on a Vite project.

## Mode `setup` (one time per project)

Every setup step that changes files ends with its own commit (`chore(design): setup step N, <name>`), because each step is a checkpoint Nadav may want to revert alone; the run log `.omc/design-runs/setup-<date>.md` is appended after every step, not at the end. **Setup is resumable, and a rerun never redoes finished work.** Step 1 prints a resume table before anything else: one row per **Setup artifact** (Hard rules), its path, exists yes/no, and the step that creates it. Every step whose artifact already exists is reported as `already in place` in one line and skipped; only missing ones run. So a run that stopped at step 9 continues at step 9, and a rerun on a finished project changes nothing and ends with the table. If Nadav wants a step redone anyway, he names it (`/ux-setup step 4`) and only that step runs.

Say `clean slate already done on <date>` and go to step 1. Otherwise, find every trace of an older design/skill/memory system so nothing overlaps with the new stack. Inventory only, no deletion yet:
   - Project agent config: `.claude/skills/*`, `.claude/commands/*`, `.claude/agents/*`, `.agents/skills/*`, `.cursor/rules/*`, `.codex/*`, `skills-lock.json`, hooks in `.claude/settings.json` / `.claude/settings.local.json` that mention design, ui, ux, taste, guard, lint-motion, impeccable, superdesign, stitch, pro-max.
   - Design docs and state: `DESIGN.md`, `design.md`, `PRODUCT.md`, `design-system.md`, `style-guide.md`, `tokens.json`, `design-plans/`, `.impeccable/`, `.superdesign/`, `superdesign/`, `.stitch/`, `.design/`, `docs/design*`, `docs/ui-audit/`, `.omc/skills/*design*`, `.omc/plans/*design*`, design entries in `.omc/notepad.md` and `.omc/project-memory.json`.
   - Rules text: sections in `CLAUDE.md` and `AGENTS.md` about design, UI, fonts, colors, motion, RTL from the old system.
   - Never touch product code (app/, components/, lib/, styles) in this step; tokens and CSS are handled in steps 2-4.
   - **Mechanical sweep, so nothing is missed.** Run `~/nadavai/plugins/nadavai/scripts/design-legacy-sweep.sh` (file names and file contents; the patterns and the allow-list of files this setup creates live in that script, nowhere else) and show its output. Add every hit to the inventory unless it is product code or a product asset.
   Show the full list with paths and one line on what each is. Ask Nadav to approve. Then: copy everything approved to `.omc/archive/design-legacy-<YYYY-MM-DD>/` (a local, untracked convenience copy; `.omc/` is git-ignored) and write the tracked `docs/archive/design-legacy-<YYYY-MM-DD>.md` manifest (paths, one line each, the commit hash that removed them); git history is the durable archive, so the removal is a normal commit, remove the old sections from CLAUDE.md/AGENTS.md/README (keep non-design rules), remove the matching hooks and settings entries, delete design entries from `.omc/notepad.md` and `.omc/project-memory.json`, and commit `chore(design): archive legacy design system before setup`.
   **Verification (mandatory):** run `design-legacy-sweep.sh --verify`; it must print nothing. Anything printed: back to the inventory. Evidence: the empty output, the manifest, `git status` clean. Only after this, step 1.

1. **Detect.** Read CLAUDE.md, package.json, the lockfile, components.json (if any), `TOKENS`, `SHELL`, `.claude/rules/*`, `.github/workflows/*`, `.husky/` or `lefthook.yml`, `capacitor.config.*`, `public/manifest*`. Report: framework family (Next or Vite) + version, Tailwind version, shadcn yes/no and base, current font, `dir="rtl"` on `<html>` yes/no, count of physical direction classes: `grep -rEo "\b(-?(m|p)[lr]-|-?(left|right)-|text-(left|right)\b|rounded-[tb]?[lr]\b|rounded-[tb]?[lr]-)" UI_DIRS --include=*.tsx | wc -l`, existing project rules about UI, existing hooks and CI, mobile shell (Capacitor / TWA / PWA manifest) yes/no, multi-brand signals (see 4b). **Version gate:** if Tailwind < 4, React < 19, or Next < 15 (app router), stop here and propose the upgrade first (`npx @tailwindcss/upgrade`, `npx @next/codemod@latest upgrade latest`, or the Vite/React upgrade), because shadcn rtl mode, `@theme` tokens and the logical-utility lint assume the current stack; setup continues only after the upgrade is committed and `PM build` passes. Verify required skills are available. Evidence: the report with the recorded names (`TOKENS`, `SHELL`, `UI_DIRS`, `PM`, `DEV_CMD`).
2. **RTL infra.** With shadcn: set `"rtl": true` in components.json, run `PM dlx shadcn@latest migrate rtl`. Without: `PM dlx shadcn@latest init --rtl --base base`. Ensure `<html lang="he" dir="rtl">` in `SHELL` and a DirectionProvider when on Base UI. The RTL gate itself is already in place and needs nothing installed: the global pre-commit hook scans the staged class strings on its own (see step 14a). `eslint-plugin-tailwind-rtl` is offered on top of it, never instead: try it once, and if it reports more than a handful of false positives, say so and drop it — on a Radix codebase it flags `side="left"` (a component API that flips itself) and the word "left" in an English test title, and its `--fix` writes `side="start"`, which Radix rejects; TherapyFlow measured 23 findings and 23 false positives. If it does earn its place: `PM add -D eslint-plugin-tailwind-rtl`, add `tailwindRtl.configs["recommended-tailwind"]` to the flat eslint.config (its rules are warnings, so every gate runs eslint with `--max-warnings=0`), run `npx eslint --fix --max-warnings=0 .` once here (the only whole-repo fix; later modes touch only their own files). Either way the project keeps a source-scanning guard of its own in `lint:ui`, because the hook only reads single lines and a class list can be split across several. This rewrites real layout classes across the app, so it is a visual change: screenshot the three busiest screens before and after, show both, and apply the visual change gate before committing; review the diff, anything inside a `dir="ltr"` element stays physical. Evidence: the physical-class count after, and `PM build` passing.
3. **Font.** One Hebrew family (Rubik or IBM Plex Sans Hebrew, subsets hebrew+latin) as `--font-sans` in `TOKENS`; Next: next/font; Vite: `@fontsource-variable/<family>` or self-hosted woff2 with `font-display: swap`. `--tracking-normal: 0`; max two families app-wide. This changes how every screen reads: screenshot two text-heavy screens before and after and apply the visual change gate. Evidence: `document.fonts` shows one family, plus the approved comparison.
4. **Tokens.** (a) House base first: copy `~/nadavai/templates/design/base.css` next to `TOKENS` as `base.css` and add `@import "./base.css";` right after the tailwind import; delete any project-level duplicates of what it defines (type scale, motion, z-index, safe-area vars, focus ring, reduced-motion rule) — except one that is load-bearing, which is the normal case for a z-index scale: an app's layering is usually the scar of a real stacking bug, and the house names collide with it silently because both sides are called `--z-*`. Keep the project's, drop only the names it does not use, and record the deviation in DESIGN.md with the bug that produced it. It is structure only; the app keeps its own colors, font and radius personality. (b) Audit `@theme` in `TOKENS`: colors count, OKLCH share, accents, dark mode. If no coherent theme: ask Nadav for a tweakcn preset name or a reference screenshot, then `npx shadcn@latest add https://tweakcn.com/r/themes/<name>.json`. Target: one accent, neutrals, three status colors, three radius values, 4px spacing, a `--ring` focus token, dark mode wired (`prefers-color-scheme`, or next-themes with `attribute="class"`). Replace stray hex in components with tokens. Tokens change colour across the whole app, so this is the largest visual change in setup: screenshot the three busiest screens before and after, in light and dark, show them side by side and apply the visual change gate per screen that shifted. Evidence: `grep -rE "#[0-9a-fA-F]{6}" UI_DIRS --include=*.tsx | wc -l` before/after, the approved comparisons, and a dark-mode screenshot.
4b. **Multi-brand check (always ask, never assume).** Look for signs of more than one brand/vertical/tenant: any `data-*` attribute used as a brand scope (`data-brand`, `data-vertical`, `data-tenant`, `data-theme` beyond light/dark — grep the attribute, not one spelling of it), theme switch code, multiple logo/color sets, route groups or build modes per vertical (e.g. clinic vs salon), and a second entry point in the bundler config. If found, ask Nadav with the recommended option first: "shared root + one file per vertical". On yes: `DESIGN.md` at root holds what is shared (type, spacing, radius, motion, RTL rules, states); `design/<vertical>/DESIGN.md` holds per-vertical color roles, tone, references; tokens in `TOKENS` scoped as `[data-brand="<vertical>"] { ... }` on top of the shared `@theme`; PRODUCT.md gets one section per vertical. From here on, every Impeccable critique/harden/document and every DoD run happens once per vertical (set the brand attribute via a query param or env for the DoD routes). `design/<vertical>/DESIGN.md` and a flat `design/<vertical>.md` are both accepted, and whichever the project already uses is the one to keep; the gap scan looks for either.

   **A second bundle is not a second theme.** When the vertical is its own build (a separate entry, a build mode, its own bundler output) rather than a scope on one document, it needs its own port, its own report directory, and a fixture in place of a QA login, because its identity is baked in at build time and there is nobody to log in as. Three things follow, none of them optional: `DOD_VERTICAL` in the DoD config (`dod-shared.ts`) so the products do not share a score; its build profile comes from an env seam, never from the committed real-tenant profile, so the fixture and the shipped app cannot swap places; and every dependency that the main app takes for granted is checked against that bundle, since a shared component drags its imports across the entry boundary — see the analytics rule in `~/nadavai/rules/posthog-init.md`.

14. **Enforcement (rules that run without me).** (a) Pre-commit: nothing to install. Nadav's global `~/.git-hooks/pre-commit` (from nadavai) scans the staged class strings for physical direction utilities, then runs eslint `--max-warnings=0` and impeccable detect on the staged files of any repo whose package.json has `lint:ui`. The RTL scan is the hook's own and depends on no plugin, because until 17/09 it was eslint-plugin-tailwind-rtl's job and a project that declined that plugin silently had no commit-time gate at all while its rules file promised one. Never add husky or lefthook: husky rewrites `core.hooksPath` and silently disables the global commit-msg, pre-push and Cloudflare deploy hooks. If the project already has husky, move its commands into `package.json` scripts and remove it (ask first). Prove the gate, never assume it: stage a throwaway file containing `className="ml-4"`, run the hook, and show the rejection; then check the other direction by running the same scan over the whole of `UI_DIRS` and showing that it reports nothing, because a gate with false positives is a gate someone will switch off. Revert both. This step is a measurement, and it is what caught the hook passing `ml-4` on TherapyFlow. (b) CI: copy `~/nadavai/templates/ci/ui.yml` to `.github/workflows/ui.yml` (written for pnpm 10; on npm, yarn or bun replace the setup action and every `pnpm` command with `PM`; merge into the existing CI if one runs lint already; keep `dod` as its own job so screenshots upload as an artifact); `ARGOS_TOKEN` as a repo secret only if Nadav gave one. (c) PR template: copy `~/nadavai/templates/ci/PULL_REQUEST_TEMPLATE.md` to `.github/` and fill `{PM}`. (d) Lighthouse CI budget: `PM add -D @lhci/cli`, copy `~/nadavai/templates/ci/lighthouserc.json` to the root, fill `{PORT}` and `{START_CMD}` (`pnpm start` on Next after a build, `pnpm preview --port PORT` on Vite), add the product routes from `e2e/dod/routes.json` (never the styleguide), run `PM exec lhci autorun` once locally so the first numbers are known (the `lighthouse` job in `ui.yml` enforces it from now on); if the project already has `lighthouse.yml`, merge and delete the old one — and `ls -a` for a `.lighthouserc*` dotfile while you are there: LHCI prefers it over the file you just wrote, so a stale one from an old launch keeps winning in silence and the report describes a config nobody has read in a year. TherapyFlow had one measuring the SPA shell twice. (e) `STATUS.md` (or BACKLOG.md, whichever the project uses): a "UI system" line with the date, the DoD scores and the styleguide route. Commit `chore(design): ui rules, gate and enforcement`. Evidence: the rejected test commit, the workflow file, `git log -1`.

End with a table: step, what was done, evidence, what remains.

## Mode `audit` (deep, every screen, no fixes)

This is the full preparation Nadav wants on an existing project before any renovation starts. Cover every screen, not only the main one.

1. Confirm every **Setup artifact** (Hard rules) exists. If not, say "run `/ux-setup` first" with the missing list and stop.
1b. **Measurement first.** `node e2e/dod/routes.mjs` (so every route is included), then `PM dod` on all of them and `PM exec lhci autorun`: every later step reads these screenshots (`reports/dod/screens/<slug>__{375,1440}__{light,dark}.png`) and scores instead of taking them again. Evidence: `reports/dod/dod.json`, `.lighthouseci/`.
2. **Inventory.** List every route (Next: `find app -name page.tsx`; Vite: the router file), every shared layout, and every component under components/ with its usage count. Mark screens as critical (auth, signup, onboarding, checkout, payment, account) or normal. Save to `docs/ui-audit/INVENTORY.md`. Evidence: the file.
3. **Per screen, in inventory order** (one screen per step, evidence after each): `/impeccable critique` (the skill names it, per the carve-out in working-style.md); look at the four DoD screenshots of the route from step 1b; note visible issues. For critical screens also `/interfaces:better-interface` (the owner for an existing screen; `interface-review` needs a diff and there is none here). Append findings to `docs/ui-audit/<route-slug>.md`.
4. **Codebase-wide.** Detect with the plugin's launcher, which is newer than the pinned npm package (`"$(ls -d ~/.claude/plugins/cache/impeccable/impeccable/*/skills/impeccable/scripts/impeccable | tail -1)" detect UI_DIRS`); `npx eslint . ` (tailwind-rtl rule count); `grep` for stray hex colors, physical direction classes, `transition: all`, fonts loaded; `/improve-animations` (Emil, read-only) if any motion exists. Evidence: counts and the report paths.
5. **Detailed measurement.** `lighthouse_audit` via the chrome-devtools MCP on the three main screens for the detailed report (the numbers per route already come from step 1b). Evidence: the three reports.
6. **Tokens vs reality.** Compare DESIGN.md tokens with what screens actually use; list drift (colors, radii, fonts, spacing outside the scale). Evidence: the list.
7. **Renovation plan.** Every finding from steps 3-6 ends in this file as a `- [ ]` item with a priority, or is marked fixed, or is recorded in DESIGN.md as a knowing exception: nothing stays a sentence in the report. Write `docs/ui-audit/PLAN.md`: per screen a P0-P3 list as `- [ ]` checkboxes with file:line (the `screen` mode ticks them, and `next` reads them), the recommended order of `/nadav-design screen <name>` runs (critical + most P0 first), what is shared (fix once in components/ before screens), and an estimate per screen. Show it to Nadav and stop. Nothing is fixed in this mode.

## Mode `screen <name>` (one screen, new or redesign)

1. **Brief.** Write a 10-line brief for the screen: purpose, user, data source, and every state (loading, empty, error, success), acceptance: RTL, 375 and 1440, dark mode, keyboard, touch targets >= 44px, reduced-motion, real Hebrew copy, tokens only. If the screen renders content a user typed or uploaded, the brief also lists its hostile cases (mixed Hebrew and Latin on one line, a 300-character word, a pasted URL, an emoji-only entry, a failed upload, a reported item) and the `.claude/rules/ui.md` user-content rules apply. Show it; wait for OK.
2. **Build or redesign** with shadcn components only (add via `PM dlx shadcn@latest add <name>`), tokens from globals.css, logical properties. For a redesign: keep behavior, strings, routes and data code unchanged.
3. `/impeccable critique` on the screen (the skill names it, per the carve-out in working-style.md).
4. Fix what it named with Impeccable's own fixers, inside the existing design language: `/impeccable polish` for the P0/P1 findings, then `/impeccable harden` (edge cases, long text, RTL, states). Nadav types both; you apply nothing by hand that these two cover.
5. If the screen has motion: ask Nadav to type `/nadavai:review-animations` (user-invoked by design); apply the Block items.
5b. **Second opinion, only when the screen is critical** (auth, signup, onboarding, checkout, payment, account deletion) or introduces a new complex component: `/interfaces:interface-review` on the working tree; apply HIGH findings. For a new complex component also `/interfaces:break` and fix what breaks. For auth, payment, account deletion or anything touching data or money also `omc ask codex` on the diff (grok when codex is out of quota), per Nadav's second-model rule; report its findings and what was done with them. Otherwise skip this step and say "skipped: not critical".
6. On the screen's files only (`FILES=$( { git diff --name-only HEAD -- UI_DIRS; git ls-files --others --exclude-standard UI_DIRS; } | grep -E '\.(tsx?|jsx?)$' )`; if it is empty, skip this step and say so, never run the tools without arguments): `PM exec impeccable detect $FILES` clean and `npx eslint --fix --max-warnings=0 $FILES` clean (never the whole repo inside a one-screen task; the pre-commit hook and CI run the full pass); then the Vercel web-design-guidelines skill as a static lint on the changed files (a11y, forms, focus, animation, Intl), and `vercel-react-best-practices` + `vercel-composition-patterns` on the same files (waterfalls, bundle, memo, composition); fix the findings or explain each one left.
7. **Blast radius first.** If the diff touched anything shared (a file under `components/`, a layout, `TOKENS` or `base.css`), list every route that imports it (`grep -rl "<ComponentName>" UI_DIRS`) and run the DoD on all of them, not only this screen; when it is a token or a layout, run every route. Say the number of routes the change affects before running. Only when the diff is confined to this screen's own files: `PM dod -- --grep "<slug>__"` for this route only (run `node e2e/dod/routes.mjs` first so the route and its state variants are in `routes.json`; the all-routes run belongs to audit and ship); read that route's score in `reports/dod/dod.json`. Score must be 100; CI enforces it. A deduction that cannot be fixed stops the step (Hard rules): report it with the cause, do not commit the screen.
8. Open the four screenshots the DoD run just wrote (`reports/dod/screens/<slug>__{375,1440}__{light,dark}.png`); do not take them again. Show them to Nadav next to the before shots and apply the **visual change gate**: he says keep, change or revert, for each thing he names. Fix what he names and re-run step 7. Nothing is committed on my own judgement of how it looks.
8b. **Approval in a separate lane (never self-approve).** Spawn the `oh-my-claudecode:verifier` agent with the diff, the DoD score and the four screenshots; it checks the brief's acceptance list from step 1. Commit only on its approval; on rejection go back to the step it names.
9. Commit with Conventional Commits; tick the screen's checkbox in `docs/specs/*.md` and its items in `docs/ui-audit/PLAN.md` where they exist. Report: score, screenshot paths, what changed, and what was left out with its decided home (PLAN item or DESIGN.md exception; never an open sentence). Ask before starting another screen.

Optional after a critical screen, only if Nadav asks: `/interfaces:interface-review`, `/interfaces:break`.

## Mode `plan <feature>` (before any code, one feature)

0. **Is the problem clear?** If the problem, audience or whether to build at all is unclear: `/intent:strategize` and `/intent:investigate` (ember) first; if user research already exists: `synthesize-research` (nadavai) before the PRD; if Nadav is about to interview users: the `mom-test` skill (wondelai product-strategy) shapes the questions. Otherwise say "problem clear" and continue. Evidence: the brief or the one line.
1. **PRD.** `/write-spec` (bundled in the nadavai plugin) for the feature; answer its questions from the repo and PRODUCT.md, ask Nadav only what cannot be inferred. Save to `docs/specs/<feature>.md`. Evidence: the file, Nadav approved.
2. **Job.** `jobs-to-be-done` (wondelai product-strategy): one job statement per user type, saved into the same spec under "Jobs". Evidence: the section.
3. **Flows and IA.** Intent plugin (wren): `/intent:journey` for the end-to-end flow, `/intent:organize` for IA and navigation, `/intent:wireframe` for the screen structure, `/intent:localize` for the RTL and Hebrew notes. Output as Mermaid in `docs/specs/<feature>.md` under "Flows": happy path plus two failure paths, every decision node has an exit. Evidence: the Mermaid renders.

Ask which first.

## Mode `ship` (before release and after)

0. **Pre-flight.** Every **Setup artifact** (Hard rules) exists or stop with the missing list. The QA credentials resolve and the last DoD run has `unreachable = 0`. `git status` clean, `PM build` passes, and if `docs/ui-audit/PLAN.md` exists every P0 in it is closed. Evidence: the checklist.
1. **Full audit.** `npx @lhci/cli@0.15.x autorun` with every route from `e2e/dod/routes.json` in `lighthouserc.json` (mobile preset), plus `lighthouse_audit` via the chrome-devtools MCP on the three main screens; the bar is the quality bar in Hard rules. Fix every failing assertion using the chrome-devtools skills (`a11y-debugging`, `debug-optimize-lcp`) and, when the app is deployed on Cloudflare, its `web-perf` skill; re-measure until `autorun` passes. Evidence: the autorun summary.
2. **Israeli accessibility and privacy.** Run the `israeli-accessibility-compliance` skill checklist; fill the accessibility statement skeleton from setup with the real facts (contact, date, known gaps); confirm the privacy page is linked and, if PostHog replay is on, that masking is in place (`maskAllInputs`, `maskTextSelector: "*"`) and routes with personal data are excluded. Evidence: both page URLs and the replay config lines.

4. **Visual regression baseline.** Argos is wired since setup: run the DoD once with `ARGOS_TOKEN` set, open the build, approve it as the baseline; from now on `argos-pr-review` reads the diffs on every PR. ## Mode `retro` (after a run; improves this skill, never the project)

0. Find the run: the newest `.omc/design-runs/*.md` when present (untracked; absent on a fresh clone or worktree, then reconstruct from `git log` and ask Nadav to paste the checklist), plus `git log --since` its date, `reports/dod/dod.json`, `.lighthouseci/` or the Lighthouse CI output, `docs/ui-audit/`, `.omc/notepad.md`. Evidence: the list of sources found.
1. **Step audit.** For every step of the mode that ran, one row: done with evidence / done without evidence / batched with another step / skipped / failed, with the line that proves it. "Done without evidence" and "batched" are failures of this skill, not of the project.
2. **Threshold audit.** DoD, axe, Lighthouse, `lint:ui`: met or not, and whether any threshold was lowered. Compare only the numbers, because setup legitimately edits routes, ports and reporters: the `minScore` / `maxNumericValue` lines of the project's `lighthouserc.json` against the template's, `--max-warnings=0` still in `lint:ui`, `e2e/dod/dod-shared.ts` byte-identical to the template (projects never edit it), and the score gate line present in `.github/workflows/ui.yml`. Any difference is a P0 finding.
3. **Tool audit.** Every skill, plugin, template or command that was missing, errored, needed a permission prompt, was outdated (`npx` version vs plugin version) or produced output that was not used. Time per step when known.
4. **Question audit.** Questions asked that the repo already answered (breaks Nadav's rule), and decisions taken silently that should have been asked.
4b. **What Nadav has not done yet (the gap scan; retro proposes it without being asked).** Check the project against the whole loop, not only the mode that ran: every **Setup artifact** present; the **Loop position** rules (both in Hard rules); `docs/ui-audit/PLAN.md` items still open; routes in the app missing from `e2e/dod/routes.json`; screens changed since the last `screen` run (`git log` on `UI_DIRS`) without a DoD run; a `ship` older than the last release tag; the weekly PostHog review overdue; multi-brand verticals without their own `design/<vertical>/DESIGN.md` (or flat `design/<vertical>.md`; check both before reporting one missing, and count a separate-build vertical too — it is the one most often forgotten). Output: the next one to three commands, in order, with the reason.
4c. **Tool freshness.** `claude plugin marketplace update` + `claude plugin list --outdated` (or the equivalent), `npm view` on `eslint-plugin-tailwind-rtl`, `@argos-ci/playwright`, `@axe-core/playwright`, `@lhci/cli`, `impeccable` vs what the project and the templates pin; new open issues on shadcn RTL (#10274, #8454, #9519, #9233) that changed status. Propose upgrades, never apply them here.
5. **Proposals.** Two lists. (a) For Nadav: what he forgot or has not run yet (from 4b), as commands. (b) For the skill: concrete edits, each tied to a finding above: to `SKILL.md`, the `ux-*` wrappers, `~/nadavai/templates/*`, `~/nadavai/rules/*`, or the memory file. Say what stays as is and why. Show the list and stop for Nadav's approval. Nothing in the project is touched in this mode.
6. **Apply (after approval).** Edit in `~/nadavai` (the source of truth), run the `skill-creator` skill's review on the changed SKILL.md when a mode misfired or did not trigger, and always its `quick_validate.py` on every changed skill (frontmatter values with a colon must be quoted; its "Unexpected key argument-hint" message is expected, Claude Code supports that key), commit with Conventional Commits, push, `~/nadavai/update.sh`, and add one line with the lesson to the memory file `ui-ux-setup-prompt.md`. If the retro found a project-specific repeatable workflow, `skillify` it into `.omc/skills/`. Evidence: the diff, the commit, the update.sh tail.

## Which mode when

**Existing project:** `setup` (step 0 clean slate) → `retro` → `audit` → Nadav approves `docs/ui-audit/PLAN.md` → `screen <name>` in PLAN order (shared first, then critical) → `ship` → `retro` → after launch: `plan <feature>` → `screen` per screen; `ship` step 8 weekly.

**New project:** `shadcn create --rtl` → `setup` (step 11b direction pick) → `retro` → `plan <feature>` → `screen <name>` per screen from the plan → `audit` after 4-5 screens → `screen` for the fixes → `ship` → `retro` → launch.

`next` (or no argument) tells Nadav where the project is in this order and what to run. `retro` after every run, so the skill learns from each project.
