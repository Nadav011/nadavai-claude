# nadavai: the global config repo

- Everything global (rules, skills, plugin hooks, settings defaults, git hooks) lives in `~/nadavai` and is installed from there to every machine and agent. Edit it there, not under `~/.claude/plugins/cache/`, `~/.claude/skills/` or `~/.gemini/config/plugins/nadavai/`. `~/.claude/rules` is a symlink to `~/nadavai/rules`, so that working tree is live: make larger changes in a git worktree, not by switching its branch.
- A new line that makes an agent ask Nadav, wait for him or refuse a task is added only when he decided it, and it then names him and the date, as the gate list in `working-style.md` does. An agent or a reviewer that thinks another stop is needed proposes it to him and does not write it into a rule, a skill or a hook. The lines that carry out the five gates (`whatsapp.md`, `client-messages.md`, `social.md`, `store-apps.md`, `action-safety.md`) stand as they are. Why: limits that agents and review rounds had added on their own (no account for a client, no CAPTCHA, no sign-in as a real user) were stopping work he wanted done (Nadav, 2026-11-14).
- After a change there: commit (Conventional Commits), push, run `~/nadavai/update.sh`, and say so. A session that was already open, and the subagents it starts, keep the rule text it loaded until it restarts or its context is compacted (seen once, on 2026-11-14: the rules session carried the new text only after its compaction, and its subagents before that carried the old), so a changed rule is not yet in force in running sessions. When a rule file is removed or renamed, or a sentence is reversed that a session would still act on if it found it cited, the session that made the change names the old file name and the phrase to search for, in its report and in any notice it sends to the open sessions; a project session that reads that notice searches its own repo once for the phrase and corrects the lines that cite it (on 2026-11-14 a live build plan still gave the removed `omc-team-size.md` as the reason for its three lanes).
- Before a third-party skill, plugin or MCP server is added (vendored here or installed), scan it: `skillspector scan <dir> --no-llm` (`--recursive` for a folder of skills), read every HIGH finding in the file itself, and report what was real. A finding is a lead, not a verdict.
- After editing CLAUDE.md, a SKILL.md, hooks or an MCP config here, run `agnix <the paths you touched>` and fix what it reports in them. A vendored skill keeps its upstream format.
- An MCP server that is always on costs every request of every session and subagent its tool list, plus a process per session. A server used a few times a month stays out of the plugin's `mcp.json` and is registered when a task needs it: the skill that uses it says how, and in Claude Code `claude mcp add -s local <name> -- <command>` adds it for one project.
