# Machine load: pick the light path that keeps quality and speed

- Before any heavy or repeated local work (test databases, replays, builds, browser runs, parallel agents), choose the setup that loads this computer least while keeping full quality and the fastest wall clock. Load is never the reason to skip a test, a review or a check. Why: on 2026-10-19 five full Supabase stacks (45 containers) ran at once for SQL tests that needed only Postgres, and the 16-core machine sat at load 28-41 for hours (Nadav, 2026-10-19).
- Use the smallest component the check needs: plain Postgres instead of a full Supabase stack when only SQL runs; one long-lived server with a pre-migrated template database, cloned per test (`createdb -T`), instead of a fresh stack per run; one shared build or browser instead of one per agent.
- Every test still starts from a clean state (a fresh clone, a fresh database), never from a database another test wrote to.
- Bound the heavy part: a lock or a cap on concurrent stacks and replays, and tear each one down as soon as its run ends.
- Heavy jobs go through `heavy-slot` and databases through `pg-pool` (`ci-policy.md`).
- Wait by blocking, never by fast polling: `docker wait`, `pg_isready -t`, `flock`, or a loop that sleeps 2-5 s and uses bash builtins, not a git/awk/cut/sha256sum/psql fork per iteration. Never poll CI or a Claude task output in a loop at all (`ci-policy.md`). Why: on 2026-10-23 agent wait loops ran 1,200-1,700 forks/s on the MSI and cost about 20% system CPU.
- Throwaway test Postgres (Supabase lanes, scratch containers) runs with `-c fsync=off -c synchronous_commit=off -c full_page_writes=off` or a tmpfs data dir; real or shared data never does. Why: those flushes queued behind every other write on the MSI's NVMe and froze Orca, while a test that starts from a fresh database loses nothing when crash durability is off.
- A throwaway container from an image that declares a volume (every `postgres` image) starts with `--rm`, or with `--tmpfs` on its data dir, or is removed with `docker rm -fv`, never plain `docker rm -f`. Why: plain `-f` leaves the anonymous data volume behind; on 2026-10-26/27 agents' `docker run -d postgres:16` with a `docker rm -f` trap left 176 dangling volumes (7.2 GB) in two days, and 19 more in one hour.
- Playwright test configs and scripts launch Chromium with `ignoreDefaultArgs: ['--disable-dev-shm-usage']` (in `use.launchOptions`, or in `chromium.launch()`); add it when you touch a config that lacks it. Claude Code's Playwright MCP gets the same through `PLAYWRIGHT_MCP_CONFIG` (set by `update.sh`); the Codex and Grok Playwright MCPs do not yet. Why: Playwright always passes that flag, so Chromium keeps its shared memory in `/tmp`, which is on disk here; on 2026-10-26 Chromium was 36-52% of the ext4 journal blocks while Orca froze on the disk, and `/dev/shm` holds 32 GB in RAM.
- An extra server is fine when it is the lighter path (a staging database, a container on another machine, a cloud instance), as long as it holds no real customer data. Anything that costs money goes through the paid-service approval gate.
- The second machine (omarchy) runs CI for every repo and is weaker; do not move agent work there unless a measurement shows spare capacity, because a slower CI queue slows every agent. This laptop is also a CI host for therapy-flow-v2 branch heads (`nadavai-slot.service`), so local heavy work competes with CI here too.
- Measure before and after (load average, container count, run time) and say what the choice saved.
