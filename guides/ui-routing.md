# UI/UX and product routing (one owner per step)

Moved from `rules/working-style.md` on 2026-11-07 to cut always-loaded context; the summary there
points here. Read this before choosing a UI, UX or product skill.

- Unclear problem, audience, or whether to build at all: intent agent ember (`/intent:strategize`, `/intent:investigate`). product-innovation frameworks are citable references, not the owner.
- Flows, information architecture, wireframes, and new interface copy: intent agent wren (`/intent:journey`, `/intent:organize`, `/intent:wireframe`, `/intent:articulate`).
- Reviewing an existing screen whose code is in the repo ("go over it", "what should I fix", "what is wrong"): `/interfaces:better-interface` (it dispatches to the better-* skills itself; never call a better-* skill as the entry point). Reviewing a diff: `/interfaces:interface-review`, which only Nadav can start (he types it); without him, run `/interfaces:better-interface` on the changed screens. A design with no code yet: intent agent vigil (`/intent:evaluate`).
- Building, restyling, or fixing a screen's visual design in code, after a review named the problems: impeccable (`polish`, `harden`, `clarify`, `adapt`, `layout`, `typeset`; `critique` only when Nadav asks for it by name, or when the nadav-design skill names it in a step: audit step 3 and screen step 3); never `craft`, `bolder`, `overdrive` or `delight` on an existing app, because they swap its own look for the generic Impeccable look. Motion, mobile feel, copy fixes and accessibility have their own owners below and win over this line. OMC designer only when impeccable is unavailable.
- A site that presents (a portfolio, a landing or showcase site, a scroll film, 3D), anything built from a reference Nadav gave ("like this", a link, a video, a screenshot), or a demo for a client: the nadav-design skill, track `site` or `client-demo` (`tracks/site.md`, `tracks/client-demo.md`, `shared/reference.md` in the skill folder). It names the motion and 3D skills (gsap-*, threejs-*, optimize-three, awwwards) and when each loads; do not start from one of them directly.
- Accessibility: better-accessibility fixes code; israeli-accessibility-compliance answers IS 5568 and Hebrew RTL compliance; `/intent:include` for design-level decisions.
- Copy already in code that reads badly: better-writing. Motion: animate builds, review-animations critiques a diff, improve-animations audits a codebase. Components: shadcn (automatic when components.json exists); variants of a real page: `/interfaces:variant`. "Feels like a website on the phone" or touch feel in a web view: mobile-native; native iOS conventions only: ios-hig-design. Whether a platform gets a PWA install or a store app: `rules/store-apps.md` and the store-apps skill.
- Product documents: the product skills bundled in nadavai (`write-spec` for a PRD, `synthesize-research` when research already exists, `competitive-brief`); product ideas: `/intent:strategize`. Engineering handoff of a decided design: intent agent rune (`/intent:specify`). Usage data after release (events, funnels, session replays, errors, feature flags, experiments): the PostHog MCP server (`mcp__plugin_nadavai_posthog__exec`) and PostHog's skill files under `~/.claude/plugins/marketplaces/posthog/skills/` (read the file; the plugin is off), which are also the only error tracker; `metrics-review` only writes the summary; defining metrics before release: `/intent:measure`.
- Six skills copied from the wondelai library live in nadavai (`jobs-to-be-done`, `mom-test`, `ux-heuristics`, `ios-hig-design`, `conversion-optimization`, `microinteractions`): use one only when Nadav names it, or when the nadav-design skill names it in a step (`mom-test` before user interviews, `conversion-optimization` for funnel features, `ios-hig-design` for a Capacitor iOS target). Their keywords ("fix the design", "design review", "usability audit", "loading state") never make them the owner.
- Code planning, execution and verification stay with OMC, within `ci-policy.md` (scoped checks plus the CI status of the sha), and every UI task ends with the browser evidence the Verification section of `rules/working-style.md` requires.
